# 最终评论的复述验收

此流程检查开发者能否从评论理解已核定的判断，可独立于 Darwin 使用。规则来源是[中央表达与验收](../central/review-rules.md#最终报告的表达与验收)；[真实报告改写示例](../central/report-examples.md)提供首批材料。本次独立生成与读者复述结果见下方执行记录。

内联来源固定为 clarity 的 `670002e995780573d6aba83f7dfb936b3f8e30eb` 版本：[主规则](https://github.com/Yikai-Liao/skills/blob/670002e995780573d6aba83f7dfb936b3f8e30eb/clarity/SKILL.md)与[文本写作参考](https://github.com/Yikai-Liao/skills/blob/670002e995780573d6aba83f7dfb936b3f8e30eb/clarity/references/text-writing.md)。

## 准备材料

为每条历史报告保存原评论 URL、所审版本、PR 简介、原文、新文，以及独立核定的事实表。事实表包括触发、结果、原因、影响范围、等级、恢复目标和证据状态。旧版与新版使用同一组事实；例子中的历史判断不直接作为当前缺陷。

先核对改写有没有遗漏关键条件、扩大影响、把静态推演写成实测、新增未证后果，或将一种修复方案变成唯一答案。发现事实缺口时先补依据；已核定材料有而评论没有的前提，才可由编辑补入。原报告里未证明的附加风险若删去，应记录原因，如首个示例的文件损坏假设。

记录真实运行的控制面 SHA、入口与加载文件；如声称使用了 clarity，还需核对实际加载方式和版本。当前中央入口已内联相关规则，不依赖运行时另行安装 clarity。仓库中的候选改动尚未部署时，不能说线上评论已使用它。

## 先让读者复述，再核对事实

给读者的材料只有最终评论和 PR 简介，不提供事实表、原分析、理想答案或另一版本评论。要求用自己的话回答，并为每个答案引用评论中的依据：

1. 什么操作在什么条件下出问题？
2. 谁会看到什么后果，范围多大？
3. 当前机制为什么导致这个结果？
4. 处理需要恢复什么行为或补齐什么决定？

缺少依据就回答“未说明”，不得自行补全。另请读者指出需要追问的对象、条件、因果或处理目标。熟悉代码的维护者随后对照事实表判断答案；合法修复方案可以不同。

如果使用模型前置检查，须用未读取原分析、事实表与另一版本的新上下文，保存原始回答，再交给持有事实表的人核对。模型可能凭技术背景补全缺口，因此通过检查不代表真人理解。编辑与复述检查不自动增加生产模型调用或发布阶段。

首个样例的必要答案是：关闭失败留下本次创建的结果文件；禁止覆盖已有文件使同一轮重试失败。只说“关闭出错所以无法提交”仍缺少关键因果。只清理本次创建的文件也是处理目标。公开评论不重复声明默认静态审查方式；事实核对仍应拒绝虚构实测。

## 小规模真人验证

起步可选 12 条已核实的历史报告，邀请 3 名开发者；这是建议配置，不是统计结论。按不同解释困难选样，避免全是同一种文件错误。

随机分配旧版和新版，并交错阅读顺序；同一开发者只读同一问题的一个版本，避免先读带来的背景影响比较。先冻结事实表和判断标准，再收集回答。记录读者对该项目的熟悉程度。

| 指标 | 记录方式 |
| --- | --- |
| 理解正确率 | 四个问题分别判为正确、错误或未说明，保留原回答与依据 |
| 理解耗时 | 从开始阅读到提交复述答案的时间；结合答案正确性比较 |
| 澄清需求 | 追问原文及缺口类型：对象、条件、因果、处理目标 |
| 语义偏差 | 是否误判触发、影响范围、确定性或修复要求 |

逐条检查是否仍需靠源码补全才能理解主张；验证主张真假可以打开源码。事实错误和关键理解缺口分别登记，不用整体偏好掩盖。resolve 率、字数、句长和标题数量不能替代理解结果。

保留每条报告的新旧回答差异、分歧与样本限制，依据反复出现的具体误解调整规则。样本尚未执行时记录“未执行”，不以“新版更顺”作为验收通过。

### 并发提交问题

```markdown
> [!WARNING]
> **P2：并发提交失败时会覆盖维护者留存的工作稿副本**

同一轮审查中，两次 `submit_review` 并发提交不同内容时，两个调用都可能先通过 `submitted` 检查。若 A 先写入工作稿副本并成功独占创建发布结果文件，B 随后会覆盖工作稿副本，再因结果文件已存在而以 `EEXIST` 失败。维护者事后回查的副本于是可能与可信发布器读取并发布的内容不同。

这是因为工作稿副本在独占创建发布结果文件之前就以覆盖方式写入。应确保只有获准提交的内容能写入两份结果；并发提交不同内容时，两份结果须逐字一致，失败调用不得覆盖成功调用留下的副本。见 [`review-tools.ts:128–129`](https://github.com/Qiyin-Tech/agentic-review/blob/8ea95dfafc72b1ef1d6a924a63a0ef7ce4f67f9c/.github/pi-extensions/review-tools.ts#L128-L129)。
```

### 凭据测试问题

```markdown
> [!CAUTION]
> **T1：凭据边界测试接受了可交给审查 Agent 的写权限 token**

若 Pi step 的环境配置通过 `vars.REVIEW_WRITE_TOKEN` 注入一个有 GitHub 写权限的 token，Runner 会把它交给审查 Agent。项目约束要求 Agent 始终只读，GitHub 写入只能由 Agent 结束后的独立可信 publisher 执行；该额外 token 会让 Agent 绕过只读 `GH_TOKEN` 的限制。当前测试的 `assertSafeSource` 只拒绝 `secrets` 和无法追踪的 `steps` 来源，没有限制 `vars`，因此这个错误配置不会触发断言，周边只读 token 和 job 权限检查也仍会通过。

应让测试拒绝未经批准的 `vars` 写 token 来源，同时继续接受 `REVIEW_AGENT_MODEL`、`REVIEW_AGENT_BASE_URL` 等非敏感配置及获准的只读 token。验收时该写 token 探针应被拒绝，合法配置仍应通过。见 [`review-runtime.test.ts:35–40`](https://github.com/Qiyin-Tech/agentic-review/blob/d3a10572b7b7dd1760f1b628378431956243ca01/test/review-runtime.test.ts#L35-L40)。
```
