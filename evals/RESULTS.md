### T1：新 finding

旧版：

```md
> [!WARNING]
> **P2：RC 分支创建会触发重复发布**

**📌 问题与触发**

开发者首次用 `git push` 创建 RC 候选发布分支时，预期同一次创建只执行一次候选版本发布。`base` 没有 `create` 入口，而 `head` 在 `.github/workflows/publish.yml:13` 新增了分支 `create` 事件入口；同一次创建会同时产生 `push` 和 `create` 两条满足 build 条件的路径。两条路径虽然使用相同 concurrency group，但 `cancel-in-progress` 仅在 `push` 事件为 `true`，因此 `push` 先开始、`create` 排队后仍会在前者完成后继续，无法保证只运行一次。[查看所审版本](https://github.com/example/backend/blob/12b2a63fe8e6c81f82d08e2dc2137f94c41e3079/.github/workflows/publish.yml#L13)

**💥 影响**

同一候选版本会被重复构建、重复推送镜像并重复更新部署包，已确认造成额外构建及远程调用；目前没有证据证明数据损坏或生产事故。

**🛠️ 依据与处理**

根因是新增 `create` 事件入口与已有 `push` 入口共同满足发布条件；concurrency 只控制并发，不保证两条事件路径去重。修复应让同一次 RC 创建只触发一个事件发布，同时保留从已有 commit 创建 RC 的发布入口。未执行测试，验收仍待检查这两个场景：首次创建 RC 分支只发布一次，从已有 commit 创建 RC 仍能发布。
```

新版：

```md
> [!WARNING]
> **P2：创建 RC 分支时同一候选版本重复发布**

**📌 问题与触发**

开发者首次用 `git push` 创建 RC 候选分支时，预期同一次创建只发布一次候选版本；实际 push 和 create 两条事件路径都会满足构建条件。push 先开始、create 排队并在 push 完成后继续时，共享并发组也不会让第二条路径自动消失。

本次修改新增分支 create 事件入口，而原有 push 入口仍在；`cancel-in-progress` 仅在 push 事件为 true，因而不能消除这两条路径的重复执行。

**💥 影响**

同一候选版本会被重复构建、推送镜像并更新部署包，额外消耗构建资源和远程调用。当前证据未证明因此发生数据损坏或生产事故。

**🛠️ 依据与处理**

根因位于所审版本的 [publish.yml:13](https://github.com/example/backend/blob/12b2a63fe8e6c81f82d08e2dc2137f94c41e3079/.github/workflows/publish.yml#L13)，该处同时允许 push 与 create 路径进入发布条件。修复应保证同一次 RC 创建只有一个事件发布，同时保留从已有 commit 创建 RC 的发布入口；最小验收是首次创建只发布一次、已有 commit 创建仍能发布。未执行测试，验收场景仍待检查。
```
