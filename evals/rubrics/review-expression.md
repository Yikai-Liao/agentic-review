# 文本评判目标

只评生成文本，不审查代码，不重新判定输入已经固定的缺陷。比较同一案例的两份匿名输出，不知道哪个版本新旧。先判断每份是否满足目标，再给 X/Y/tie 偏好及 clear/slight 把握，不使用绝对分数差。

总评目标：读者只看总评也能知道这次 PR 改了什么、为什么改，以及有没有要处理的问题。结论在前，随后简述修改前后、涉及流程和支持判断的关键结果；不能省略变化介绍或用内部机制清单替代。不要求固定句数或字数，无空历史状态和文件/协议枚举。多个问题逐项导航，不能为简洁漏掉问题。局部范围及关键证据缺口可见，未发现问题不等于测试通过或批准合并。作者报告的测量在句内写明来源和测量对象。总评不附加保证清单、默认静态审查声明或未执行事项；无新问题时“已核对的风险”是例外，每项须有场景、阻止机制，并带固定事实给出的代码定位，缺定位的条目不合格，补造事实没有的路径同样不合格。

Thread 目标：新 finding 按中央表达与验收规则检查读者理解，不要求固定栏目或段数。读者懂相关语言、读过 PR 简介，但没有参与本轮审查；仅凭评论就应能复述操作与触发、可观察后果、原因和恢复目标。必要项目规则就地解释，同一对象名称稳定，每段增加新信息。技术名词服务因果证明；避免一长段塞满条件或把调查日志交给读者。后续 evidence 能恢复哪个版本改变了什么判断，区分已修复、部分修复、反证、接受边界，保留影响判断的具体范围，不追加默认审查方式的声明。

硬性事实门槛：不添加原始事实没有的缺陷、损害或测试结论；不漏掉本轮新问题和历史状态变化；不把已接受写成修复，不扩展决定范围，不把局部结论写成整个 PR 已验证。未变化历史状态默认只留工作稿，显式复核请求须直接答复；仍有旧问题未解决时不能声称全部解决。不为了显得更完整而补写推测。偏好必须受这个门槛约束。

报告每个 case：X_pass、Y_pass（满足用户目标，不只是语法正确），preference X/Y/tie、margin clear/slight、具体理由及各自不合格点。总偏好不覆盖单个硬性事实错误。

先分别检查两份输出是否合格，再比较偏好。“比另一份短”不等于 pass：摘要照抄 finding/evidence/schema/thread_updates 等内部协议名、汇报不存在的历史/人工确认项，均不满足业务摘要目标；即使整体更好也记该份不合格。总评的历史导航、新 finding 关联另一个原问题需要原 thread 链接；直接发布到该原 thread 的 evidence/request_reply 无须再附自链接，但仍须保留改变判断的代码或决定来源。不能把已知回复位置与修复证据混为一谈。逐例检查具体文本，不只列较差版本的缺陷。

可理解性与事实保真分别判定。对每份 finding 逐项回答上述四个问题并引用评论原句作为依据；无法回答就记“未说明”，不得用评委持有的固定事实补全。固定事实只用于随后核对答案是否正确。缺少关键前提或因果关系，即使事实没有错误也不合格；遗漏触发、扩大影响、把静态推演写成实测、新增未证后果或强制唯一修复方案均不合格。字数、短句和标题数量不能替代这些判断。

需要隔离技术背景补全或开展真人验证时，按[成品复述验收](../report-comprehension.md)准备读者材料；匿名偏好和模型试跑本身不代表真人理解效果。

公开评论重复声明“静态审查／推演”“未执行测试／未模拟故障／未复测”，或添加与当前结论无关的防御性说明，均视为表达不合格。事实保真由正面准确的陈述实现，不要求把工作稿中的每项验证记录输出给读者。
