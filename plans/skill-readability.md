# agentic-review Skill 可读性改写计划

## 背景与目标

当前 Skill 的入口和共同协议先介绍规则分类，再用高密度术语串联要求。维护者需要反复拆句、跳转文件，才能还原实际工作流程。本次以人的阅读和理解为先：读者应能说明它做什么、从哪里开始、遇到疑点怎么判断，以及何时交付。

可读性不是压缩字数。允许用完整句子和必要示例换取理解；同时保留审查能力、权限边界和中央接入行为。计划及样稿均已获批准，正式 Skill 已完成改写并补做 clarity 结构修订。维护者同意第 6 步以作者自查收尾；第 7 步已完成获授权的 12 例比较与失败记录，但未通过改进验收，没有全文实际读者测试或完整行为无退化证明。

方法哲学同时包含两项目标：正确理解、传递和完善用户目标；推动高效、优雅、可维护的实现。不是只防止需求传递失真，也不是只检查代码是否功能正确。

## 推荐方案

- 开头先用一两句话讲清方法哲学：为什么纵向区分需求、架构、计划和代码，又用横向审查视角贯穿各层；这如何让 Review 贯穿 Agent 开发流程。
- 先建立这一认识，再说明结构和实际工作顺序。不是删除核心抽象，而是让读者理解它们为何存在，能据此判断未列出的情况。
- 可以使用术语和名词，首次出现就地解释；优先采用已有、符合大众常见理解的名称，避免自造词及直觉歧义。必要时用具体动作、判断条件和结果解释概念，不以删掉全部术语为目标。
- 将特殊情况放到发生它的步骤附近；仅特殊任务需要的长说明保留为按需参考。
- 先展示一段有代表性的改写，让维护者确认行文风格，再推广到相关文件。
- 将人工可读性验收与 Agent 行为回归分开，不能互相替代。

### 1. 开篇先给出方法哲学

拟用以下两句话作为样稿，而非先列规则或文件：

> Review 的目的，是帮助 Agent 正确理解、传递和完善用户目标，并推动高效、优雅、可维护的实现。我们纵向按需求、架构、开发计划、代码编写等层级组织审查对象，横向从意图对齐、可维护性、可靠性、安全、验证等视角检查问题，让同一套审查与复核方法贯穿整个 Agent 开发流程。

纵向和横向都在开篇直接举例，不能只解释一边、让读者自行猜测另一边。接着用一张小表解释各层的问题：

| 纵向层级 | 要回答的问题 |
|---|---|
| 需求 | 是否正确理解用户真正要达成的结果？哪些遗漏、矛盾或取舍需要澄清，才能完善目标？ |
| 架构 | 方案能否承接目标？责任和接口是否清楚，是否引入了可避免的理解与协作成本？ |
| 开发计划 | 工作安排能否形成完整交付？依赖、集成、验证和推进顺序是否合理？ |
| 代码编写 | 实现是否满足约定行为？运行成本是否合理，结构是否清晰，后续维护是否容易？ |

完善目标包括发现遗漏、澄清矛盾和提出有依据的取舍；需要改变用户偏好或已确认范围时，交还有权决定的人，不擅自替用户改目标。“高效、优雅、可维护”需要通过现实运行成本、清晰的责任与接口、必要机制和真实修改任务来说明，不以代码短、抽象少或符合审查者风格代替判断。

横向视角回答“从什么角度检查”：意图对齐、可维护性、可靠性、安全、验证；性能和测试等代码专有方法在相应入口介绍。共同方法回答“凭什么下结论，以及如何确认问题已处理”。三者在同一位置讲清，不让读者自己从目录名推导。

用现有执行快照案例说明意义：用户要求主定义和子定义都不受后续编辑影响，需求却被改成只冻结主定义；后续设计、代码和测试全部一致，也不能证明用户目标得到了满足。沿这条关系找到最先需要改正的位置，而不是每层重复报告同一个问题。

在相关方法正文中复用需求的“假设与决定”、架构的“理由与决定”、可维护性的真实修改演练和性能的批量调用例子，分别说明如何完善目标与改进实现。不能让整套说明只剩下“原样传递并实现已有要求”。问题反馈给有权修改或决定的人，再根据新版本和证据复核处理结果。

这是一套可组合的方法，不是强制流水线：可以只审某一层，也可以围绕一个问题跨层追踪；“贯穿流程”不代表每次检查所有层级和所有视角，更不代表 Skill 接管开发调度。

### 2. 入口先讲全貌，再引导操作

`SKILL.md` 的阅读顺序拟为：

1. **为什么这样审查**：上述哲学、两个维度及一个跨层例子。
2. **选择本次要审的内容**：选产物与视角；普通审查采用各层默认范围，“只审 X”才缩小范围。将对象链接放在对象说明旁边。
3. **完成一轮审查**：确认对象、版本与授权 → 理解目标和当前需要澄清的内容 → 按选定视角检查产物及相关连接 → 验证问题或改进机会 → 交付结论。这是阅读导航，详细规则分别在相关步骤链接处展开。
4. **处理结果和下一轮**：谁修复、何时需要上层决定、新版如何复核；完成 Review 不代表没有问题或批准交付。

独立审查要求和默认只读边界放在开始调查之前。历史记录在恢复要求时引出，实测规则在需要实验时引出，分批/恢复/委派放到对应任务情形；不能把重要边界藏到读者不会进入的参考文件里。

### 3. 各类正文采用相同的讲解顺序，而非强套同一张表

每篇先讲它要解决的问题和判断思路，再说明如何调查；难点紧跟正例与“什么情况下不应报问题”，最后给出交付或复核要求。无需每篇都有相同数量的标题、例子或步骤。

- **共同流程**：`protocol.md` 顺着调查过程讲，删除面向内部维护的开场职责清单；详细规则各有一个明确归属，入口只负责概览和导航。
- **结论**：`findings.md` 先解释“已证明的问题、现在必须决定的事项、可证实的改进机会、当前验证缺口”为什么不同，再给具体门槛。保留 `defect` 等标识，中文解释在前。
- **四类产物**：先讲本层如何理解、传递或完善目标，以及如何支持高效、优雅、可维护的实现，再说明哪些细节应在当前阶段确定；随后展开方法。默认、条件触发、明确委托的区别原样保留，不把所有专项变成默认必做。
- **横向视角**：先讲这项视角在寻找什么，再展示在不同层级如何取证。复用现有离线、恢复、接线与租户例子，不给每层复制一套共同规则。
- **记录与复核**：`review-state.md` 按首次记录、收到修订、判断状态、恢复中断任务、可选委派组织，去掉 W1/W2 一类无助于理解的标题前缀；保留覆盖状态与问题状态的区别。
- **代码专有方法**：性能先解释如何比较现实成本，测试先解释“错误被放过、合法变化被拒绝、没有新增检测能力”三种问题，再进入盘点、分组与证明。保留完整分支触发、边界独立价值、删除证明与去重要求，不能用“避免重复测试”取代它们。
- **模板**：字段提示改成读者能直接回答的问题，保留必要 ID 和状态字段；每个模板说明何时使用，不把可选模板变成每轮必填表。维护者扩展说明继续放在 `assets/specialization.md`，不抢占常规阅读路径。

### 4. 文字和格式的具体标准

- 一段围绕一个问题展开，先说要做什么及其理由，再补适用条件；避免用斜杠和分号压进多个概念。
- 标题使用读者的问题或动作，如“找到当前阶段必须满足的要求”，不使用“独立义务与到期点”一类需要二次翻译的词组。
- 解释用短段落，顺序用编号，并列选项用列表；表格只承担真正需要对照的内容，代码块只承载代码、格式或简短流程。
- 核心术语首次就地解释，不增加一份必须先读的术语表；首次可从某个按需文件进入的读者，也应能理解该文件的关键概念。优先通行名称，含义符合常见理解。代码字段、API、状态枚举和必要专业名词保持准确，不做全局机械替换。
- “见证”改写为具体的触发场景和证据；“最强反证”首次说明为“主动寻找能证明这个疑点不成立的解释”；测试中的 `fingerprint` 等必要结构解释其用途后再使用。
- 用完整说明消除歧义，不增加泛泛的“认真、全面、严谨”提醒；安全禁令保持明确，其他重复否定改为正确做法及其适用条件。
- 不预设压缩比例。记录主入口和真实加载路径的长度、跳转次数，增长要对应必要解释，而不是把冗长内容藏到更多文件中。

## 验证

### 人的阅读验收（首要）

面向两个实际读者：需要理解和维护方法的人，以及依此执行审查的 Agent。按用户补充的五项能力验收，不用标题数、句子长度或文件数量代替阅读效果：

| 读者应能做到 | 在本 Skill 中如何检查 |
|---|---|
| 识别目的 | 读开头就能说清：完善用户目标，并支持高效、优雅、可维护的实现，而不只是找代码错误 |
| 找到相关信息 | 给出普通审查、跨层专项、复核或维护任务，能从入口找到需要的说明，辨认必读与条件阅读 |
| 建立正确理解 | 能解释层级、视角、共同规则如何配合，举出纵横实例，并区分跨层取证与扩大审查范围 |
| 就地跟随推理或执行 | 打开相关章节后，能在当地找到术语含义、适用条件、依据、动作和结束条件，无须来回拼接关键推理 |
| 正确使用或修改方法 | 能完成判断与交付、处理复核；维护者也能找到扩展说明，知道哪些规则应复用、哪些内容由本层定义 |

逐段检查是否让读者承担了不必要的工作：目的不清、术语变化、关系未说明、关键依赖相距过远、嵌套过深、主线中断、混合抽象层级、过早抽象、重复信息、压缩表达或没有解释的意外行为。发现后直接调整正文和内容位置，不靠追加提醒或外围说明书补救。

每项抽象先说明它解决什么问题，再用于组织细节；术语保持同一含义。可以按需链接较长细则，但完成当前判断所需的理由和关键区别应就地交代。用户从某个参考文件直接进入时，也应能理解该文件的关键概念。

完整句子多了、文本长了不自动判失败；人为阅读失败也不能靠 Agent 多数票掩盖。

### 规则与接入核对

逐项核对：独立依据和即时有效决定；各层默认/条件/窄审范围；反证、根因归并及关闭条件；性能与三种测试证明；历史接受不等于修复；覆盖未完成不等于通过；工作稿与恢复；只读、实验授权、可信发布和中央固定输出边界。保留必要的证据记录粒度，不以简化表述为由删掉调查。

实施阶段先运行 `pnpm exec tsx --test test/review-instructions.test.ts`。修改测试后运行 `pnpm check`；整套改写收尾运行一次 `pnpm test`，后续仅因新改动或未解决失败扩大检查。当前计划阶段不执行这些测试或安装依赖。

测试仍验证包内链接闭合、改名锚点、中央预载/恢复集合、缺规则时失败、六项默认职责和现有 JSON 示例。按契约更新旧文字断言，不新增断言强制哲学段必须逐字不变，也不将关键词出现当作理解正确。

### Agent 理解与行为回归

- 主目标固定为“同一审查方法更易理解和正确执行”，不是本轮重新优化 finding 风格或改变缺陷门槛。
- 先从现有案例中固定小组，覆盖四层、横向组合、跨层归因、目标澄清、可维护性改进、零问题、阶段合法省略、复核/接受与权限；初始材料可从 Q01、A01/A03/A05、P01、X01、B01、C01 选起，并从 requirements、simplify 分组补齐目标完善与实现质量的正反例。保留未用于样稿的新场景作最终回归，范围不足不能以样本胜出代表整套通过。
- 代码部分必须包含行为、性能、测试失真/过约束/冗余，以及关联记录与状态；最终集合及各例验收在生成前固定，缺合适正反例才补用例，不把预期写入运行任务。
- 新旧版使用相同事实、模型、档位、工具和重复次数，各自新上下文，分别加载完整固定规则；中央案例通过各自完整中央入口，不混用新旧 reference。
- 采用独立匿名成对评判，并人工核实遗漏、误报、归因和权限差异。表达、正确性、读取/工具/token 成本分别记录；不能用“更简洁”抵扣漏查或扩权。评判的模型与成本在样稿门确定，不默用历史模型。
- `evaluate.ts` 的固定事实表达结果不是本次方法的端到端验收。本次保留路径便于比较，但仍需验证实际入口的按需读取；如使用其准备/盲评功能，先核对适用任务，不为套工具改变被测任务。
