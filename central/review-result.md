# 中央 Review 结果

本文件只定义中央 Action 的持久化、GitHub thread 更新和可信发布格式。finding 门槛、严重度和根因归纳来自可信 `agentic-review` Skill。

## 1. 中央工作稿

使用 workflow 提供的隔离目录 `$REVIEW_WORKSPACE_PATH`。中央入口用 `notes.md` 保存一份工作稿，`review-progress.json` 保存文件进度，提交工具自动保存 `review-result.json` 最终结果；不另建 `review.md` 索引。工作稿作为限期、受权限保护的 Actions artifact 保留。

准备阶段已经写入固定请求身份、版本、可信规则恢复入口与进度路径。明确覆盖[中央默认层级](review-rules.md#选择审查层级)时，`notes.md` 保留选择及来源；固定事实和文件进度使用已有记录。

`notes.md` 的记录粒度使用[共同工作稿规则](../skills/agentic-review/references/review-state.md#分开记录调查进度和问题状态)：保留调查中已取得、但公开结果未包含的支持证据、关键前提和未完成项；没有 finding 也保存必要依据。覆盖状态使用 `review-progress.json`；`review-result.json`、PR Thread、回复和 Review 正文已有的内容直接引用。

笔记随调查形成，与文件进度在同一次 `bash` 或 `codemode` 调用中保存，不为整理笔记另开回合；最终归纳直接使用当前上下文和已有记录。长工作稿按相关路径或符号定位读取。按风险从高到低调查：认证授权、数据写入与迁移、公共契约、并发与状态，再到测试、文档和生成物。

选择 code 时，每个实质变更单元在登记对应文件 complete 前，先提出最可能使它出错的具体场景：哪种输入、时序、调用方、失败或部署顺序会让新行为偏离契约；再沿代码确认该场景被什么机制阻止，或会造成什么后果。单元涉及多类高风险边界时，每类至少检查一个场景。场景成立时按 finding 门槛继续调查；被阻止时在 `notes.md` 记下场景、阻止机制及其代码定位。版本号、格式、文案和生成物同步等机械性变更只注明无需场景的理由。读过该文件的 patch 或相关源码并完成上述检查后才登记 complete，不按路径模式或整份清单批量登记未读文件。收到收尾通知前，`submit_review` 要求全部 scope 内覆盖完成，不得以范围大为由提前结束；收到收尾通知后，未完成项保持 pending，不生成假 complete，直接提交已审部分的结论，发布器据文件进度列出未审查文件。

准备阶段已记录默认 scope。调查前对照本轮请求核定；显式请求改变范围时调用 `set_review_scope` 更新 `mode`、`ranges`、`rationale` 和 `explicit_text`，否则直接使用默认值。每个区间包含比较起止 SHA 和足以恢复范围的 targets；保留默认计划中的全部义务，只有显式限定时才缩小范围。最新实际 scope 是下一轮恢复范围的唯一来源。

workflow 在 Agent 启动前按完整 PR 与默认计划各区间的文件并集生成 `$REVIEW_PROGRESS_PATH`（`review-progress.json`）的 `ledger`。该文件只包含 scope 决策和文件进度，不保存请求身份或机器状态。保留每个条目的 `path`；首次调查和重开项完成必要调查后登记为 `{"path":"src/example.ts","status":"complete"}`，继承完成项保持原状态。`source_reviewed` 条目由可信准备阶段写入：该文件在已通过审查的来源 PR 中审过，合入后的内容与来源 PR 的 head 一致；它们视为完成，不得改写，也不必重复逐文件审查。未完成条目保持 `pending`；局部范围外条目使用 `out_of_scope`，full 范围不允许排除条目。文件进度是唯一的覆盖状态，不另建工作稿完成清单。

可信代码持有请求身份、默认计划和清单摘要，并决定发布状态；Agent 只维护审查判断和文件进度。发布器校验清单未缺失；scope 内仍有 pending 时照常发布已审部分，并据文件进度列出全部未审查文件，该轮不形成完整 audit。工作稿内容用于恢复调查，不以文件非空或笔记字数代替调查证据是否充分的判断。finding 的证明与去重仍满足通用方法，最终结果仍通过固定 schema 校验。automatic 使用完整 PR 的 `full` scope，完整覆盖由可信历史完成项和本轮调查共同构成。

输入中的 `Workspace resume manifest` 提供本轮工作稿、进度与上一轮结果参考的准确路径。准备阶段已迁移选中历史的 `notes.md` 和 `previous-review-result.json`；当前进度以 `review-progress.json` 为准。同一快照恢复已完成状态；automatic 接入同 base、当前历史中的可信完整 audit 后，未直接变化的完成项也默认延续。上一轮只发布了部分结论时，评论请求同样延续已完成项：同一快照只审查剩余文件，新提交只重开直接变化的文件。直接变化、新增和历史未完成项保留 `pending`；当前 thread 对应文件以及每次 `pr_comment` 请求的范围内文件仍按请求复核。

按 `central/github-context.md` 先调查增量，沿新变化和相关旧记录中的依赖前提定位影响；契约、调用方、保护、状态前提或相关讨论改变时，将对应完成项重开为 pending，局部更新受影响的判断和反证，保留其余证据。其余历史完成项直接继承，不因笔记简短或未写无问题依据而重查；缺少依据确实妨碍本轮影响判断或疑点核验时，只补查相关部分。scope 变化会自动将旧 `out_of_scope` 条目重置为 `pending`。

## 2. 历史 thread 状态

把存活候选与当前 PR 已有 inline thread 和最新回复比较，一个根因只保留一条：

- 未变化的历史问题：保留工作稿中的核对结论，不生成 thread update，默认不在本轮正文逐条或按数量重报；
- 原问题已修复、被证据推翻、所缺决定已取得，或具体代价已被明确接受：`resolved`；依据按[共同状态规则](../skills/agentic-review/references/review-state.md#状态变更需要什么证据)逐项核对；
- 影响、成本或严重度扩大：`severity_increased`；
- 已解决问题重新出现，或当前实现超出既有确认范围：`reintroduced`。

文档同步记录已确认决定时保持 `resolved`，不能仅因决定写入当前 head 而标记 `reintroduced`。

默认总评的历史问题导航只列本轮 `thread_updates` 中的状态变化，每项一行标题、状态和原 thread 链接，完整证据留在该 update。已关闭的问题仅在本轮实际关闭时报告一次，后续未变化时留工作稿。状态用 `⚠️ 风险升级`、`🔁 问题重现`、`✅ 已关闭`。T2→T1、P2→P1/P0 或性能从有界路径变为无界/常见路径属风险升级；测试问题升级为生产问题时更新原 thread。

显式 PR 评论请求复核或汇总历史状态时，在 `body` 按请求范围答复，包含必要的未变化状态、依据和限制，不因此生成 `thread_updates`；这类答复按请求组织，不强套默认总评结构。显式 thread 请求在 `request_reply` 中针对请求答复，即使结论未变，`body` 不重复答案。

thread update 的 `evidence` 先给出处置结论，区分已修复、原判断被反证、已接受边界；接着解释改变判断的代码或决定如何覆盖原触发，保留剩余触发及接受范围。简单变化可合为短段，每项事实只展开一次。

说明改变判断的依据时，用真实来源定位，例如“[aaaaaaa](原 commit URL) 的 `src/export/refund.ts:28` 让两种失败复用退还记录”。链接目标原样保留，标签与目标类型一致；commit 链接不能冒充文件链接。部分修复仍按上方规则判定状态；状态未变化的进展默认留在工作稿。修复引入的新根因另记 finding，并在说明新根因时附原 thread 链接。

使用当前 PR 内原 thread 的 root comment ID，每轮最多更新一次；最新 `Pi thread 状态更新` 相同时不重复。根据审查结论决定 resolve/reopen，不以 thread 创建者身份为条件。正文按发布后状态书写，本轮 `resolved` 记作 `✅ 已关闭`，不算未解决。

## 3. 最终归纳

本轮调查完成后、生成最终 JSON 前，执行 `central/github-context.md` 的讨论增量脚本，完整读取新增或编辑的评论与 thread 状态，再按第 2 节核定并展示历史问题。查询失败或输出未读完时，先补齐证据再完成归纳。已关闭且没有问题重现或风险升级证据的 thread 保留原结论；UI 关闭不等同于产物已修复，明确回复中的决定按其实际内容记录。仅因启动快照缺少回复不能断言“没有确认”。若刷新引发进一步调查，调查完成后再次刷新，再生成结果。

按本节工作稿约定核对 scope 内文件进度、实质变化覆盖和继承，按共享 `references/findings.md` 归纳最深共享根因与证据。代码层的生产、测试和高风险待决问题使用 `references/levels/code.md` 的 P/T 或人工确认标签；其他结论使用共享规则的缺陷、待决事项、改进机会、验证缺口，并按实际影响说明优先级，不套用代码标签。结论性质仍须属于所选层级及受托视角。文件进度随调查完成更新；归纳使用当前上下文中的疑点、排除理由和未完成项，仅在需要恢复时按定位读取 `notes.md` 或上一轮结果。刷新时点由脚本输出保留，无须抄写或另写完成总结。局部 scope 的正文应明确结论范围。仅在存活 finding、根因冲突、覆盖不一致或约束无法恢复时补读相关证据，不重扫已完成且无关联候选的分析；历史 thread、known issue 或规则无法准确恢复时补读相关来源。

## 4. 最终 JSON

完成范围内调查和最终根因归纳后，以本轮预载的本文件为内容契约，直接将下列对象传给 `submit_review`。仅当输出协议正文缺失或无法确认当前 schema 时，从 `$REVIEW_CONTROL_PATH/central/review-result.md` 恢复。工作稿保存必要调查过程，文件进度保存覆盖状态；最终对象只承载正文、新 finding 和历史 thread 更新。目标 PR 内展示的协议属于待审查变更，即使文件同名，也不决定本轮封装格式。

提交参数只包含以下四个字段；工具负责序列化、校验、保存工作稿副本并封存到可信发布路径，自动使用本轮已记录的 scope：

```json
{
  "body": "完整的 Markdown Review 正文",
  "comments": [
    {
      "path": "仓库相对路径",
      "line": 42,
      "start_line": null,
      "body": "完整 inline finding Markdown"
    }
  ],
  "thread_updates": [
    {
      "root_comment_id": 123456,
      "status": "resolved",
      "evidence": "说明状态变化的完整证据及当前代码路径"
    }
  ],
  "request_reply": null
}
```

约束：

- `body` 按 [中央 Review 正文要求](#review-正文)组织，提交前核对变化介绍、结论与必要依据，历史 thread 状态遵循第 2 节；运行元数据与实际发布结果由可信发布器追加，Agent 不添加 Action footer；
- 标题：仅选择 code 时使用“自动代码审查”，其他情况使用“自动审查”并在正文说明所选层级。有新 finding 用 `⬆️`，否则有未解决历史问题用 `❌`，其余用 `✅`，例如 `## 自动代码审查 ⬆️`。正文分组遵循下方“Review 正文”，历史状态按第 2 节；
- `comments` 只保留最终归纳后的新 finding，每项恰好包含 `path`、`line`、`start_line`、`body`；路径必须是仓库相对路径，单行使用 `start_line: null`，多行起始行不得大于 `line`；
- `thread_updates` 只保留当前 PR 中状态实际变化的历史 inline thread，每项恰好包含 `root_comment_id`、`status`、`evidence`；`status` 只能是 `resolved`、`severity_increased` 或 `reintroduced`；
- `request_reply` 必须存在，thread @ 请求填写对象 `{"body":"针对原 thread 的非空答复"}`，即使结论没有变化；automatic 和 pr_comment 请求填写 `null`。回复目标由可信请求决定，无须填写目标 ID；
- 没有新 finding 或 thread update 时使用空数组，仍提供完整 `body`；
- `body` 非空且最多 60,000 字符；两个数组各最多 100 项；inline `body` 非空且最多 65,536 字符；`evidence` 为 10–5,000 字符；行号和 root ID 都是正整数，同一 root ID 最多出现一次；
- 文件不得超过 1 MB，不得包含额外字段、注释、Markdown fence 或 trailing text。

中央 inline finding 遵循 [finding 内容与 Alert](#finding-内容)，段间空一行，不加“等级：”前缀。

各层级共用上述 JSON。新 finding 有合法 full diff 位置时写入 `comments`；无法绑定有效行的遗漏或跨产物问题，在总 `body` 中保留完整证明及固定版本定位，不虚构评论行。本轮新 finding 与历史状态变化均纳入正文导航，同一根因不重复。

以下是三种请求的完整结构示例，示例事实不代表当前 PR，正文需按实际审查替换。

automatic：

```json
{
  "body": "## 自动代码审查 ✅\n\n未发现需要处理的新问题。\n\n这次要求审查意见讲清问题和修复验收，并记录问题为何关闭。现有评论和状态更新足以承载这些说明，无需改发布接口。\n\n**已核对的风险**\n\n- 同一状态更新在多轮审查中重复发布：写入前读取原 thread 的最近一条状态更新，状态相同时跳过（`scripts/publish-review.ts`）。\n- 关闭说明写入其他 PR 的 thread：写入前先做归属校验，失败时只阻断该项写入（`scripts/publish-review.ts`）。",
  "comments": [],
  "thread_updates": [],
  "request_reply": null
}
```

pr_comment（下游仓库选择需求层）：

```json
{
  "body": "## 自动审查 ⬆️\n\n本轮按项目规则审查需求变化，发现离线使用目标被缩减。\n\n这次需求稿将记录流程限定为在线提交。\n\n- 缺陷：离线用户无法记录，违背已确认的使用场景。见 docs/requirements.md:12。",

    "line": 12,

  }],
  "thread_updates": [],
  "request_reply": null
}
```

thread：

  "body": "## 自动代码审查 ❌\n\n本轮按请求复核鉴权路径，未发现独立的新问题。",
  "comments": [],
  "thread_updates": [],

生成提交参数时，按[中央表达与验收规则](review-rules.md#最终报告的表达与验收)检查成品，并核对存活 finding 与刷新后的历史 thread 状态：新 finding 的严重度与证明写进该项 `body`；历史问题的状态变化写进 `thread_updates`；未变化的历史问题按第 2 节留稿或答复显式请求。字段、类型、大小、scope 和覆盖完成条件由 `submit_review` 校验，发布器独立复核；Agent 负责内容判断，直接提交结果对象，无须先写结果文件或回读验格式。

## 中央表达模板

以下要求针对开发者实际收到的 Markdown；JSON 封装及发布器追加的运行元数据不代替正文。

## Review 正文


总评应能独立说明这次 PR 做了什么，以及审查得出了什么结论。先把结论独立成段，再介绍修改前后的行为、涉及的流程及目的，有问题时增加导航。显式历史状态请求按第 2 节答复。

变化介绍按主题组织：单一主题用短段，多个可独立理解的主题用列表，每项以简短的粗体主题开头，说明该主题的行为变化及目的。每段或每项只展开一个主题；段落之间、列表前后留空行，Markdown 的普通换行不能代替分段。不限制固定句数、字数或条目数。多主题排版见[变化分组示例](report-examples.md#多主题总评按变化分组)。

变化介绍不能省略，也不能只写“优化逻辑”等空泛结论或内部机制清单。说明主要行为与关联范围即可，不复述完整 PR 描述，不枚举所有文件，也不附加未改变机制“仍然正确”的保证清单。默认省略测试清单和未改变机制，只选有助于理解这次改动的行为与数据。

无新 finding、无本轮历史状态变化且无显式历史状态请求时，automatic 和 pr_comment 可按以下顺序表达；thread 请求用简短范围与结论，具体答复留在 `request_reply`。已有未解决问题仍决定标题为 `❌`，不把“没有新问题”写成全部已解决：

```markdown
未发现需要处理的新问题。

[按主题说明原来怎样、现在怎样、涉及流程及目的；单一主题用短段，多个独立主题用列表。]

**已核对的风险**

- [这次变化最可能出错的具体场景]：[阻止它的机制及代码定位]。
```

“已核对的风险”让读者核验本轮实际检查了什么。从工作稿记录的失败场景中选出对这次变化最关键的 3–5 项，每项写出场景、阻止它的机制和代码定位；只写本轮沿代码确认过的场景。没有实质代码变更时省略本节。不写“已检查安全性”等不含具体场景的条目，也不列与本次变化无关、未改变的机制。

用使用者或维护者能理解的行为名称，公开正文写“问题”“讨论回复”“审查范围”等，不用 finding、thread、scope 等内部标签代替含义。保留帮助理解的代码标识符；省略空历史/确认项，未变化且与判断无关的内容留工作稿。

引用作者的测试或测量时，在陈述中写清来源和对象，例如“作者对输入读取阶段的本机测速为……”。只写材料支持的结果，不另加“这不代表……”“仍待整体复测”等预防性说明；不需要介绍收益的数据可以省略。

有新 finding 或本轮历史状态变化：

```markdown
[一句结论：主要影响及处理优先级，或没有新问题]。

[按主题介绍修改前后、涉及流程与目的，不重复问题详情。]

- [严重度或状态]：[触发与后果]。[定位或原 thread 链接]
```

问题导航按影响排列，保留全部本轮新 finding 与 `thread_updates` 对应的变化及其实际状态、剩余触发或接受范围。完整证明留在 finding；接受不写成修复。变化介绍解释 PR 的行为和目的，不展开导航中的问题证明。

局部审查在结论中写明实际路径。只有缺少具体事实导致当前问题无法判断时，才说明缺什么、需要核查什么；不添加默认审查方式的说明。

总评应使读者能说出“这次改了什么、为什么改、审查结论是什么”。删去重复与无关细节，保留理解变化所需的前提。

无法绑定合法 inline 位置的 finding，在正文另列“问题详情”并使用下方完整模板；不能只用导航摘要代替完整说明。

以下模板只定义中央发布封装。成立门槛、优先级及根因归纳以共享结论契约和所选层级为准。

## Finding 内容

每条 finding 按[中央表达与验收规则](review-rules.md#最终报告的表达与验收)组织说明并完成成品复述检查。内容完整即可，不固定“问题与触发／影响／依据与处理”三个栏目；小标题、依据与验收标签按需使用。

先围绕一个具体失败场景写出问题，再编辑成可发布正文。问题性质和等级用标签表达，定级时排除的其他风险留在工作稿。下例展示内容顺序，各部分可合并，方括号不是必须逐项展开的栏目：

```markdown
> [!CAUTION]
> **P1：触发场景与可观察后果**

[操作和必要前提；最小触发后，预期与实际有何差异，谁受影响。]

[导致该结果的机制，以及影响判断的保护为何不足；代码或契约定位用于核验。]

[应恢复的约束或待批准决定；必要的原触发与相邻合法行为验收。]
```

发布前编辑是成稿的完成条件：逐句留下触发、原因、已证明的后果、依据或处理目标。只用于说明某种额外损害没有发生、风险没有更严重、某项验证未执行的句子，删除后才算完成；不把它们缩短或换个说法保留。用准确主语和条件表达范围，例如“测试接受了过期签名”已说明测试漏检，无须再声明生产系统尚未遭到攻击。标题与正文的对象、条件和等级保持一致。

Alert 与标题：

- P0/P1：`CAUTION`；
- P2/T2：`WARNING`；
- T1：`CAUTION`；
- 人工确认：`IMPORTANT`。

使用通用问题性质时，缺陷、验证缺口用 `WARNING`，待决事项用 `IMPORTANT`，改进机会用 `TIP`；已证明严重影响当前交付的缺陷可用 `CAUTION`。这些 Alert 只用于表达，成立门槛仍由共享结论规则和所选层级定义。

标题只写触发与后果，细节留正文。每段使用完整短句，关键标识符首次出现时介绍业务含义。版本与定位放在对应依据处，有真实 URL 时使用完整 Markdown 链接，标签为文件名或短 SHA，目标绑定所审版本；没有 URL 时用普通文本保留准确版本与路径，不输出方括号占位。固定版本链接已经标明版本时，正文不重复完整 SHA。行内评论复用调用方定位。正文保留理解结论所需的因果关系。具体表达式构成根因时，在解释原因处放一个带语言标识的最小代码块，不复制变化位置已清楚展示的内容。

验收场景来自已确认契约和实际路径，不把建议的实现方案变成唯一正确答案。验收写成应观察到的结果，不写成已经执行。执行记录按中央入口规则留在工作稿，不在公开评论重复声明审查方式。

性能 finding 给出规模、base/head 成本函数及数量级或复杂度证据。

测试 finding 给出对应分支证明：T1 的 violating probe、T2 change detector 的 allowed-change probe，或 T2 redundancy 的 deletion test、base/sibling 覆盖及缺失 unique witness 的证明。

单行足以表达根因时只选单行；只有声明、条件、调用或错误处理共同构成根因时才覆盖连续范围。调用方提供位置字段时，使用其 schema 要求的最小位置。


## 5. 唯一提交

最后将第 4 节的完整结果对象直接传给 `submit_review`。

`submit_review` 先校验结果对象、本轮 scope 和覆盖状态（收尾通知前要求全部完成，之后接受保留 pending 的部分结论），通过后自动写出 `$REVIEW_WORKSPACE_PATH/review-result.json` 并封存同一内容。失败返回 `queued: false` 和具体错误，按错误修正参数或进度后重试；失败不会返回完成。返回 `queued: true` / `Review queued for trusted publication.` 即本轮完成，立即结束 Agent 回合，不再调查、编辑、调用任何工具或再次提交。最终聊天回复只需简短确认，不重复输出 JSON。

后续发布由可信 publisher 完成：封存的请求身份、schema、scope 和文件进度清单是全部写入的前置条件，覆盖不完整时在正文前加可信的未审查文件提示，Check 为 action_required；通过后将正文、新 finding、请求回复及历史 thread 操作分别发布。单项失败只阻断依赖它的操作，其余继续；thread 写入仍需校验当前 PR 归属。发布器追加运行元数据与实际执行说明，汇总成功、失败和因前置失败未执行的操作；未全部成功时保留失败状态，不推进完整 audit checkpoint。Agent 只提交审查判断，不推断 GitHub 写入已经成功，也不通过其他工具发布。
