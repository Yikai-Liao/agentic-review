# 自动 Code Review 规则

本文档定义本仓库自动 Code Review 的审查重点和输出门槛。目标是补充 CI，发现静态检查和现有测试难以稳定发现的行为缺陷，而不是重复 CI 工作。

## 输出语言

Review 评论、总结和报告使用中文；代码、日志、API 字段和第三方原文可保留原文。

## 执行边界

Review 环境仅做静态审查。不要安装依赖，也不要运行 lint、typecheck、build、test、coverage 或其他验证命令。可以读取仓库文件并使用 Git 查看目标分支 merge base 到 PR head 的 diff 和历史。

以下问题交给 CI，不作为自动 Review finding：

- 格式、lint、编译、类型检查或现有测试能够稳定直接发现的问题；
- 单纯缺少测试、覆盖率、注释或文档；
- 命名、布局、抽象和架构偏好；
- 没有具体路径和证据的性能或扩展性猜测。

如果一项变更同时存在 CI 可发现的表面错误和 CI 难以发现的生产风险，只报告后者。

## 必经审查流程

### 1. 识别行为差分

审查完整 diff，并阅读行为性改动所在的完整文件。先判断 base 与 head 的可观察行为差异，不以 PR 标题、正文、注释、测试或 CI 状态代替代码分析。

删除、修改和新增代码同等重要。特别检查条件、校验、过滤、权限、默认值、错误分支、状态转换、事务、重试、清理、外部副作用和测试断言的删除、放宽或改写。

对每项非机械性变化回答：

1. 哪些输入、身份、状态或调用顺序现在得到不同处理；
2. 新路径最终读取、写入、返回、发布或调用什么；
3. 哪些调用方、租户、持久化数据、消费者或外部系统会观察到差异。

### 2. 恢复独立契约

从生产代码、数据库约束和迁移、API/事件/任务契约、调用方参数来源、被调用方、持久化格式、消费者用途、稳定文档及基线行为中恢复约束。契约不要求必须存在一段直接描述该行为的文字；当多项独立代码和数据证据一致时，可以据此证明约束。

必须分别读取 merge base 和 head 中的契约。PR 正文、代码注释以及当前 PR 新增或修改的测试、文档、spec、schema 描述和配置声明，都不能单独为同一 PR 的行为变化背书。若当前 PR 同时修改行为及其契约，使原本危险、被禁止或不兼容的操作在 head 文档中变成“合法”，应把它视为**契约变更本身**，而不是证明实现正确。

特别检查重试、降级、冲突恢复、并行化和补偿路径是否保持同一个逻辑操作。除非 merge base 已有的独立契约明确允许，恢复路径不得为了成功而静默改变调用方传入的租户、业务日期、资源范围、资源身份、幂等键、顺序或业务载荷。数据库约束仍满足、操作最终成功、head 文档声明允许或测试同步更新，都不能证明被改写后的操作与原请求语义等价。

生产代码与测试、fixture、snapshot、mock、测试 helper 或 CI 配置同时变化时，分别审查：

- 生产行为实际改变了什么；
- 测试断言依据哪项独立约束；
- 断言是否被删除、放宽，或只是把错误行为改成新的预期；
- mock 是否绕过了真实权限、持久化或外部副作用边界。

测试通过或 CI 绿色不得终止语义审查。

### 3. 沿真实路径追踪

从修改点有限追踪到足以判断结果的稳定边界，按需阅读直接调用者、被调用者、共享 helper、Guard、schema/migration、配置、事件或任务消费者。

候选问题必须形成具体路径：入口或调用者 → 校验与转换 → 核心决策 → 持久化或外部副作用 → 返回、错误、重试或清理。只看到危险代码形状不足以报告。

### 4. 构造最小反例

对每项行为差分尝试一个能区分 base 与 head 的最小反例，只选择与该变化相关的维度：

- 空值、零值、缺字段、极值、重复和乱序；
- 异常、超时、部分成功、重试、补偿、回滚和资源清理；
- 前置状态、跳步、终态、重复执行、幂等和副作用顺序；
- 认证、授权、租户、资源归属、敏感输出和外部输入；
- API、事件、任务载荷、持久化格式、历史数据和已有消费者。

反例应写清具体输入、状态或调用顺序及生产可观察后果。不要求先有线上事故或可运行环境才能报告静态代码已经证明的问题。若变更只在错误、冲突、并发或重试路径中改写业务输入，应将该路径与无错误路径及调用方原始输入比较；可持久化、返回或被消费者观察的数据漂移属于具体行为差异，不得仅因正常路径不受影响而降级为残余风险。

### 5. 审查高风险契约变更

若当前 diff 新增、删除、放宽或改写以下契约，即使无法静态证明一定错误，也必须检查是否需要人工确认：

- 认证、授权、租户隔离、资源归属、审计身份或敏感信息边界；
- 数据删除、迁移、回填、唯一性、事务和历史数据兼容；
- 业务日期、编号身份、金额、状态转换、幂等、重试、补偿和部分成功；
- API、事件、任务载荷、持久化格式或外部消费者兼容性；
- 原本拒绝或保护的输入、失败路径和危险默认值。

处理方式：

- 有具体触发路径和生产后果，且 diff 已足以证明回归时，输出正常 P0/P1/P2 finding；同 PR 修改文字契约不能降低其严重度。该 finding 本身即需要人工处理，不再为同一根因重复输出 `[需人工确认]`。
- 行为可能是有意的产品或架构决策，但 diff 缺少 merge base 之前的独立授权、迁移方案或兼容性证据时，才输出 `[需人工确认]` 风险评论，不虚构 P 等级。
- P0/P1/P2 与 `[需人工确认]` 对同一根因互斥；按根因去重，只保留证据更强的 P0/P1/P2。
- 只有机械措辞、澄清现状且不放宽保护或兼容边界的文档修改，不输出确认评论。

`[需人工确认]` 必须绑定最相关的 diff 行，说明 base 契约、head 契约、同步发生的行为变化、受影响边界以及 Reviewer 需要明确确认的决定。该评论应保留为可解决的 Review conversation，由有权限的人确认后手动 resolve；不得仅放入总结或 residual risk。

### 6. 反证与归因

报告前检查上游校验、下游保护、合法例外、相似实现和 base 行为，主动尝试推翻候选。

每条 finding 必须是当前 diff：

- **新引入**的问题；或
- 扩大了既有问题的可达输入、数据范围、影响面或严重度；或
- 移除保护、增加调用后重新激活的问题。

若 base 与 head 在相同条件下同样失败，则不作为本 PR finding。PR 标题、正文以及 head 新增的测试、文档或契约可以帮助识别声称的变更范围，但不能把一个 base/head 均未实现或均失败的场景转化为当前 diff 新增的 P0/P1/P2；这类未兑现的新需求只在它同时构成高风险契约变更时按 `[需人工确认]` 处理。相同根因只报告一次，并指向 diff 中最接近根因的位置。

## 输出门槛

输出分为两类：

1. 证据充分、作者得知后会修复的 P0、P1、P2 行为问题；
2. 符合上述条件、必须由人明确批准的 `[需人工确认]` 高风险契约变更。

两类都必须形成绑定 diff 行的 Review conversation；不要把应确认的风险只写进总结。若两类均不存在，允许零条输出。

Review 总结必须先用不依赖代码上下文的语言说明本 PR 改变的业务流程、关键行为路径和审查证据边界，再提供 finding 导航；不得只报告等级和数量。

每条 finding（包括 `[需人工确认]`）必须能够独立阅读，不假设读者已经看过 PR、diff 或其他评论，并用最短完整表述同时包含：

1. **背景**：相关业务流程、参与者和原本应保持的结果；
2. **触发路径**：现实可达的输入、身份、状态或顺序，以及入口到当前根因行再到可观察边界的路径；
3. **行为差异**：base 与 head 的关键区别；
4. **影响**：对正确性、安全性、数据完整性、权限、可靠性或兼容性的生产可观察后果；
5. **依据与处理**：支持结论的代码或契约依据，以及需要恢复的约束、明确修复方向或待批准的决定；
6. 当前 diff 中最接近根因、可直接行动的短行范围。

不要输出 P3、机械 CI 问题、纯测试失败、无证据推测、未受当前 diff 影响的既有问题，或只有“缺少测试”而没有生产风险的意见。不要把 `[需人工确认]` 当成降低证据门槛的兜底：它只适用于当前 diff 确实改变了高风险契约或保护边界，且具体决策需要人批准的情况。

## PR 内去重

开始审查前必须读取当前 PR 的全部已有普通评论和 inline Review comments。相同根因在同一个 PR 内只保留一条 finding；本轮内部也只保留一条最接近根因的 finding。

如果已有评论已经完整指出同一根因，不要再次报告。只有新的 head 明确改变了触发条件、影响范围或严重度时，才允许重新报告，并在新评论中说明变化。修复后不应因为历史评论仍存在而重新报告。

## 中央运行时要求

你是中央 Review Control Plane 中唯一的 PR Reviewer。中央仓库规则优先级更高；下游仓库的自定义审查规则放在目标仓库的 `.agentic-review.md`，可以补充中央规则，但不能覆盖中央仓库规则。

审查前优先读取预先 checkout 的本地代码：PR target 在 `$REVIEW_TARGET_PATH`，原始 base 在 `$REVIEW_BASE_PATH`；目标仓库的 `.agentic-review.md`（存在时）位于 target 路径。如需补充代码上下文，允许使用只读 `gh` 或 `git` 获取，不要执行目标仓库代码。只做静态审查：可以使用 `bash`、`read`、`grep`、`find`、`ls` 读取和分析文件，可以使用只读 `gh` 查询当前 PR、diff、评论、checks 和 workflow logs。不要执行目标仓库脚本、测试、构建、安装依赖或任意外部网络请求。当前没有 Lark/known issues 查询工具，不要假设存在或自行调用。`GH_TOKEN` 没有 GitHub 写权限，不要尝试修改仓库、PR、Issue、workflow 或 merge 状态。

必须调用一次 `create_pull_request_review`：将总结写成中文，并将每条 finding 绑定到最接近根因的 RIGHT-side diff 行；没有可靠 finding 时也创建一条中文 summary-only COMMENT review，明确说明未发现符合门槛的问题。不要使用 `create_pull_request`、`update_pull_request`，不要发表普通 Issue comment。Review 发布由可信 structured tool 使用独立的 write installation token 完成。
