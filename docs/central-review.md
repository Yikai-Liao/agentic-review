# Central PR Review Protocol

## Goal

Downstream repositories only install the Review GitHub App. The review workflow, model key, and app private key all stay in the central repository; maintainers of a target repository cannot obtain central credentials by editing their own workflows.

The central entry defaults to the code level; this round's request or the downstream Head `.agentic-review.md` or `AGENTS.md` may explicitly choose requirements, architecture, plan, or code. Priority and recovery are defined in the [central entry](../central/review-rules.md#choose-the-level). Each level chooses methods from its own scope table; the review never widens just because the skill supports more. The code level's default duties are defined in [`levels/code.md`](../skills/agentic-review/references/levels/code.md); central runs only T1 test distortion by default, T2 overconstraint needs an explicit request, test economics is excluded, and no style, maintainability, or verification-sufficiency focus is added by default. Project rules choose the level; central keeps read-only permissions, PR scope, full coverage, and trusted publication fixed.

## Event Chain

```text
Review App `pull_request`, `issue_comment`, and `pull_request_review_comment` webhooks
  -> Cloudflare Worker
  -> central agentic-review.yml (merges automatic requests)
  -> review-execution.yml (serializes review and publication per PR)
  -> prepare-review-context.ts (complete preparation of code, history, scope, and input)
  -> shaftoe/pi-coding-agent-action (read-only analysis)
  -> trusted agentic-review skill + central GitHub/result adapters + persistent workspace
  -> submit_review receives the result object and saves and seals the final JSON
  -> publish-review-run.ts (trusted validation, assembly, and publication)
  -> archive the workspace once and complete the Check
```

The Worker does four things: verifies signatures, filters non-target events, deduplicates by delivery ID, and triggers the central workflow with the Dispatcher App. It runs no target code and holds no model or Review App credentials.

Accepted automatic events are `opened`, `reopened`, `synchronize`, `ready_for_review`, and `converted_to_draft` on draft and regular PRs. New PR comments trigger through `issue_comment.created` and inline thread replies through `pull_request_review_comment.created`; the Worker keeps only human comments on PRs whose body contains a valid bot mention. Edits do not retrigger, mentions inside quotes, code blocks, or inline code do not trigger, and duplicate deliveries are dropped by delivery ID. Automatic `workflow_dispatch` requests carry `repository`, `repository_id`, `pull_number`, `base_sha`, and `head_sha`; the central workflow checks that the PR is open or merged and that the pinned snapshot matches, failing explicitly if the snapshot moved while queued. Closed, unmerged PRs are not reviewed. Draft PRs also get Checks and reviews; GitHub still blocks merging drafts. Comment requests carry no SHA; the workflow reads the PR's stored base/head when it actually starts and pins that snapshot.

Merged PRs can be reviewed after the fact through manual dispatch or comment requests. Code is still fetched by the PR's stored base/head SHAs, independent of whether the source branch or fork still exists; the original PR snapshot is reviewed, not the merge commit or the latest target branch. PR state, merged status, and merge time are given to the agent. Results are still published on the original PR, and the Check binds to the original head SHA.

Automatic requests for one PR merge pending candidates at the entry; explicit comment requests are each kept. In the execution layer, review and publication share one serial slot per PR, while different PRs run in parallel. See [automatic request merging and publication order](#automatic-request-merging-and-publication-order).

Each round pins the full review range from merge base to current head. A first investigation reads the file list and patches from the full range, reading small diffs at once and large ones by path and hunk. When the PR's history has an `Agentic Review / audit` completed successfully by the same Review App with the same base and its workspace connected, investigation starts from the incremental range from that head to the current head. Candidates come only from ancestors of the current head; ordinary merges and conflict resolution keep the baseline and their changes enter the incremental diff. Cancelled, failed, expired, or unrecoverable records never form a baseline. Full coverage combines earlier completions with this round's investigation; finding evidence and lines still bind to the full patch, and the workflow produces no aggregate diff file.

Comment request scope is driven by the text and persisted separately: an explicit natural-language scope beats a thread's implied scope, which beats the PR default. A plain PR comment re-investigates the latest PR-level request's actual scope; with no changes it still re-reviews and gives current evidence, and with changes it reviews new changes and their direct impact and fills coverage that earlier failed or was unfinished. A thread by default investigates the current problem and its direct impact, widens only when the text explicitly asks for the whole PR, and does not inherit PR-level scope history. A limited scope may restrict this round's coverage; an emphasis only changes priority. The full diff is still used for context and for validating new inline positions; reading direct-impact context within a limited scope does not claim whole-PR completion, and positions outside the full diff cannot carry invented inline findings.

Preparation records the default scope; when an explicit request changes it, the agent calls `set_review_scope` to update `mode`, `ranges` (each range's targets and comparison SHAs), rationale, and the original text. Trusted code decides the request type, and the final JSON carries no scope ID. The request and default plan are written to local context before the agent starts, and the Runner saves their SHA-256 digest as a preparation step output; the model updates only the scope decision and file progress in `review-progress.json`. After the agent, the publication step verifies the same context against the trusted digest, checks workflow inputs, and assembles `review-coverage.json`; a changed context or missing digest blocks publication. Incomplete coverage is also saved as scope history (including partial conclusions published within the time budget); only full coverage with successful publication creates a complete `audit` checkpoint. Plain PR requests find the latest PR-level request workspace through control repository artifacts by repository ID, PR, source, run, and attempt, excluding threads, raw model drafts, and the current run; earlier workspaces are read-only, and genuinely missing history, expiry, and API errors stay distinct outcomes.

The trusted workflow also builds a deduplicated JSON index of other PRs linked to head-only commits and the current PR's `closingIssuesReferences`, and writes it into the review input. The agent checks related sources per the [central linked-record flow](../central/github-context.md#4-linked-records-for-contracts-and-candidates): it reads original records on demand to recover contracts and must check the full discussion in related source PRs before submitting a new finding or confirmation. `read-related-pr.ts` reuses the current PR's pagination to include comments, reviews, inline comments, replies, and thread states so earlier decisions are not missed. Without link entries, queries do not widen; the index itself proves no relevance and is no evidence of authorization, fix, or acceptance.

`prepare-review-context.ts` prepares code, history scope, and input in one place. PR metadata reuses the raw text fetched while resolving the snapshot, and commit history comes from local Git over the pinned range; discussion reads run in parallel with the Git download, and the association index in parallel with the audit checkpoint query. Git fetches only the pinned base/head history by default; when an explicit request references an old range on another history, missing SHAs are fetched per verified records. Earlier artifacts are downloaded and verified by the GitHub CLI and attached as read-only directories, rather than passing recovery state through workflow steps.

Source attribution (`attribute-review-sources.ts`) runs before the request is persisted, since its result is written into trusted context. It walks the first-parent chain from merge base to head. When a step is exactly the merge commit of a merged PR whose head has a completed automatic audit by the same Review App, files changed by that step are `source_reviewed` if their merged content matches the source head and the base side has not moved relative to the source review's start (the merge-base of the base recorded in its Check and the source head). Otherwise (stacking, conflict resolution, taking the source version wholesale while dropping base-side changes, or a rebased source carrying history outside its reviewed diff) they are composition files: the source reviewers never saw that content, so they stay pending with their source PR. Files without a reviewed source, without a source PR, or committed directly are reviewed normally. A file takes the strictest result across steps, so a reviewed dev→test sync PR also counts its inner sources as reviewed without branch-specific rules. The `source_reviewed` list lives in context and is verified with the context digest; `submit_review` and the publisher reject model rewrites of those entries. Queries are read-only and add no trust relationship; the source PR's review record is still the Check itself. A reviewed source head may no longer be in the shared Git object store, so it is fetched on demand before comparing; any query, fetch, or comparison failure aborts the round instead of degrading to all-pending. The publisher states the number of files skipped because their source was reviewed before the review body. Thread requests review only the discussed file and do not use attribution; source-reviewed entries in the previous checkpoint carry over as completed.

Preparation copies the chosen history's workspace, earlier result reference, and file progress: the same snapshot keeps completions; `automatic` inherits a trusted complete audit with the same base so completions not directly changed carry over, while directly changed, new, and unfinished items are pending. The current thread and each PR comment request are still re-reviewed per request. The model reopens related completions when it finds indirect impact along the increment and latest discussion, updating existing evidence locally. Out-of-scope entries are the model's judgment, and changing scope resets old exclusions automatically. Rules are recovered only when preloaded rules are missing, after compaction, or when the schema is uncertain.

## Permissions for Publishing Reviews

This is the project's most important permission boundary. The central workflow mints three installation tokens with different permissions and repository scopes from the same Review App:

```text
Review App private key (only in a central Actions secret)
  ├─ Token A: target owner's repositories with the app installed; contents/issues/pull_requests/actions/checks read
  │    -> checkout, the shaftoe action, building the association index, and Pi reading linked records by number
  ├─ Token B: current target repository only; checks write
  │    -> creates the Check linked to the current Actions run before the agent starts; never given to the agent
  └─ Token C: current target repository only; contents/pull_requests/checks write
       -> trusted publication after the agent: reviews, Check completion, thread replies, resolve/reopen
```

Tokens expire after about an hour. Before the agent starts, the trusted workflow fixes Token A's readable set to the target owner's repositories with the Review App installed, read-only; the target PR cannot add repositories or permissions. Within that set, association index entries or explicit stable issue/PR references in the review input may select private records not declared at the merge base for on-demand reading. This is the intended product boundary and needs no merge-base pre-authorization. A link only creates a query entry and proves neither relevance nor business authorization. Token B is used only by trusted workflow steps before the agent; one installation token cannot read another owner's private repositories. The agent reads both merge base and PR head and interprets semantics by the head. `loaded_tools` loads no built-in GitHub write tools; `write`/`edit` are only for the isolated review workspace, and `submit_review` validates the result object, saves a workspace copy, and seals the final result.

Review and publication share one job and runner, separated by steps. Token C is minted only after the agent ends and is passed only through step inputs to the publisher and Check completion; the agent's `GH_TOKEN` and action input stay bound to Token A. The preparation entry packs `scripts` and `package.json` from the trusted control worktree checked out at the pinned `${{ github.sha }}` and gives the Base64 archive to the Runner as a step output. After the agent, the trusted launcher restores and runs the publisher from that output in a fresh temporary directory, avoiding a second checkout and never reading local scripts the agent could modify. The request context is still verified against the preparation step's SHA-256 digest. The Runner saves outputs when the preparation step ends; anything the agent outputs later belongs to its own step and cannot replace the saved code or digest. This relies on GitHub's [step output mechanism](https://docs.github.com/en/actions/reference/workflows-and-actions/workflow-commands#setting-an-output-parameter), not on the agent honoring read-only local files.

`publish-review-run.ts` validates, assembles, and publishes. Once preparation has written the request digest, the trusted publisher can assemble the recoverable scope even if later input assembly fails; no review is published when the agent did not finish successfully. After assembly succeeds it records `workspace_ready` as a step output so later publication failure or cancellation still archives that scope. The normal path archives once: `review-completed-workspace` on successful publication, `review-workspace` otherwise, including any publication report; an archive failure still fails the Check. Raw diagnostic drafts are for troubleshooting only. Target code is checked out once; the base worktree shares Git objects, and both worktrees are created with checkout hooks disabled.

After Pi ends, the trusted publisher uses the sealed and verified request identity, checks schema, scope, coverage, and that root comments belong to the current PR, then publishes the summary and this round's new findings as one review on the reviewed head and handles thread status by the conclusion, regardless of who opened the root. The summary's title, finding index, and footer are generated by the publisher from the result and discussion state; the model writes only the verdict, behavior after merge, since last review, and what was checked. A thread @ request always gets exactly one reply on the original thread root, whatever the conclusion; the trusted request decides the target, and the publisher deduplicates by request comment ID. After a new automatic summary is published, the publisher rewrites this bot's earlier automatic summaries on the PR to a single line pointing at the new one, keeping the original in a collapsed block; replies to comment requests are not collapsed. Only after the publisher succeeds can trusted completion mark the Check success; publication or completion failures never advance the complete audit checkpoint. The review footer links the time-limited Actions workspace artifact, which requires a signed-in user with central repository access. GraphQL `resolveReviewThread`/`unresolveReviewThread` also require `contents: write`, so that permission goes only to the trusted publication step after the agent.

### Time Budget and Partial Conclusions

The `review-tools` extension starts timing at `agent_start`; the budget comes from the workflow's `REVIEW_TIME_BUDGET_SECONDS` (540 seconds), and the agent cannot declare it exhausted. The first 6 minutes are investigation: if the model tries to end without submitting, the extension asks it to continue through `agent_before_settle`, and `submit_review` rejects submissions with pending items. At minute 6 wrap-up begins: the model is told to stop new investigation, refresh the discussion, and consolidate the reviewed part, and `submit_review` then accepts partial conclusions with pending items. From minute 9, `tool_call` blocks every tool except `submit_review`; if the model still does not submit, it is reminded once more and then ends, the publisher reports no `submit_review` result, and the Check fails. The Pi step's 15-minute timeout only catches hung tool calls.

Trusted code marks partial conclusions: from the file progress in `review-progress.json`, the publisher prepends the covered ratio and every unreviewed file to the review body, independent of the model's own claims. Completeness comes only from file progress: with unreviewed files, `complete_audit` stays false, no audit checkpoint forms, and the Check concludes `action_required` (blocking required checks like failure, but signaling that conclusions were published with incomplete coverage); only full coverage is success. Comment requests inherit completions from published partial results: the same snapshot reviews only remaining files; with new commits, when the base is unchanged and the path diff is readable, only directly changed and previously unreviewed files need review, and an unknown diff makes the whole scope pending again. Thread-only requests have no review body, so unreviewed files are listed in the thread reply. Automatic runs do not inherit partial progress; comment-request continuations do not update the commit's `/audit` Check, which is reassessed only by pushing a new commit or rerunning the automatic review.

## Agent Tools

Central review has paused Lark evidence and judgment: it does not download or restore the CLI archive, install the Lark CLI, read the `lark-review` environment, or inject a UAT. Lark document, wiki, and base links in the input only identify sources; they are not requested, and unread material raises no missing-evidence warning or confirmation finding.

Authorization and hourly token renewal keep running; long-lived credentials and the refresh token stay in `lark-rotation`, and the UAT keeps being saved to `lark-review` for a future restore. `central/lark-context.md` keeps the reading rules for after a restore; re-enabling requires the trusted entry to restore tool preparation, integrity checks, UAT injection, and verification of actual document permissions. Token lifecycle and restore steps are in the [deployment guide](deploy-central-review.md#4-lark-user-oauth-and-automatic-renewal).

The central workflow loads only:

- Pi built-in tools: `read`, `grep`, `find`, `ls`, `bash`, plus `write` and `edit`, which the rules limit to `$REVIEW_WORKSPACE_PATH`;
- the local submission tool `submit_review`, which takes the result object of body, new findings, earlier thread updates, and request reply directly and handles serialization, validation, and persistence.

Before final consolidation the agent runs the control `scripts/refresh-review-discussion.ts` per the central rules to read comments added or edited since the startup snapshot and changed thread states; the refresh time stays in the script output. The script uses read-only `gh`: comments and inline replies are fetched with `since`, review bodies and thread states are queried in full and only changes printed; repeated refreshes always compare against the fixed startup baseline, and failures raise errors. Deleted comments are outside the incremental protocol and are queried by ID when there is a hint. This deliberately relies on skill instructions rather than a refresh tool or a sealing gate: the sealing tool validates only the result object and coverage, does not prove the agent refreshed or adopted the latest decisions, and new replies can still arrive between refresh and publication. The trade-off does not change the boundary between the read-only agent and the separate trusted publisher. The run protocol comes from the control checkout; a new protocol inside the target PR is only code under review. The agent restores the control format before packaging and ends its turn right after a successful seal.

The shaftoe action's GitHub query tools are not loaded because they inherit the central repository context; the target PR, CI, and logs are queried through read-only `gh --repo "$REVIEW_REPOSITORY"`.

`central/review-rules.md` is the workflow's only rule entry; the trusted `agentic-review` is registered as a Pi skill. The [prompt assembler](../scripts/load-review-prompt.ts) loads the shared rules, report rules, central adapters, and the default code methods, including the full test methods. Preloading changes neither level selection nor method triggers; other chosen rules are read on demand, and an explicit level override is saved with its source in `notes.md` for recovery after compaction. Report wording comes from the skill's `references/reporting.md`; the trusted `REVIEW_LANGUAGE` adds localized headings for non-English reports. Non-code levels use the shared finding kinds rather than P/T.

PR metadata, comments, project rules, pinned-range patches, and the workspace enter the material index in `$REVIEW_INPUT_PATH`; text within budget is delivered with the first prompt, and the rest is read by path. `central/github-context.md` defines investigation and recovery at pinned SHAs and connects the association index and GitHub known issues; `central/review-result.md` defines the workspace, thread updates, and the single submission. `GH_TOKEN` is Token A, so the agent can run read-only `gh` queries against the current repository and linked repositories of the same owner, but cannot comment, merge, or modify repositories or workflows. The agent must not run target scripts, install dependencies, test, build, or make external requests unrelated to the review.

## Workspace Preparation and Incremental Resume Manifest

Central keeps only file progress, one working note, and the final result. Each ledger entry in `review-progress.json` holds only a path and status; `notes.md` keeps supporting evidence, key premises, exclusion reasons, and unfinished gaps the public result lacks, with necessary grounds even without findings. Notes are written by shared mechanism and saved in the same call as progress; content already in threads, replies, the review body, or the final result is reused, never copied, and no extra turn is spent on hand-off summaries.

Preparation creates `notes.md` for a first review with the pinned request identity, versions, trusted rule recovery entry, and file progress path; the raw request and default plan are referenced through `$REVIEW_CONTEXT_PATH` rather than copied. The initial note has a fixed JSON facts block and an empty investigation section; the agent adds only necessary investigation and never takes "done" or "no problems" from the initial file. Existing notes and the earlier result reference are copied into this round.

The manifest's `pending_files` lists files to investigate this round, while inherited completions stay in `review-progress.json`; `changed_paths` is the path diff from the earlier workspace head to the current pinned head, including reverted paths that vanished from the full list. The model starts from these changes and the latest discussion to trace indirect impact and reopens old completions as needed. `same_base` signals whether the baseline changed; missing history or an unknown diff uses `null`, distinct from a confirmed empty increment.

Paths are read from local Git's NUL-separated output; renames keep both ends, and reverted changes and file names with newlines are included. When a force-push leaves the earlier head missing locally, the summary stays `null` and whole-PR obligations remain; other Git read failures stop explicitly. The new snapshot keeps pending items and full-coverage checks, and the agent decides inheritance or reopening from the increment, latest discussion, and old premises, rereading necessary code when the earlier premises cannot be recovered. Publication still verifies request identity, pinned scope, the full file list, and the result schema; with unreviewed in-scope files it publishes partial conclusions with the list and forms no complete audit. Note format or length is never machine proof of sufficient investigation. Actual history reads, note-writing turns, and end-to-end gains still need measuring in production.

Materials are counted in `o200k_base` tokens, each keeping full text, category, and path. [Runtime preloading](../scripts/write-review-input.ts) computes the budget from the model window, maximum output, and investigation room, favoring the request, rules, current changes, and changed discussion; the current note, progress, earlier results, and the full material index compete for the same budget. Delivered index entries and text are used directly, and the first investigation reads necessary source from known locations, merging extra navigation into the same batch. Materials that did not fit keep their index entries for reading with existing tools; truncated text is never treated as complete evidence.

## The Summary Index Shows Open Problems

The publisher generates the summary index, listing every unresolved problem this bot raised under "Changes needed", "Confirmation needed", and "Optional improvements": new findings are marked 🆕, earlier problems whose severity increased or that were reintroduced this round get ⚠️ and 🔁, and "Resolved this round" is listed separately. The title states the verdict by unresolved count and never claims everything is resolved just because there are no new findings. The model's `thread_updates` record only earlier problems whose status changed; unchanged ones come from discussion state without the model re-reporting them.

When closing an earlier problem, the publisher writes a status line (status, reviewed head, one-line reason) at the top of the original comment and resolves it without a reply; it replies only on reintroduction, severity increase, or when someone else opened the root. With no new findings, no status changes, and an unchanged title, the publisher updates the latest summary in place, creating no new timeline entry or notification.

An explicit PR comment asking to check or summarize earlier status is answered in the summary within the request's scope, possibly including unchanged statuses, without creating thread updates. An explicit @ on a thread gets a targeted answer in `request_reply` even when the conclusion is unchanged; the summary does not repeat it.

## Input Trust Boundaries

PR comments and review replies are trusted decision input: an explicit reply can confirm product decisions, risk acceptance, and boundary changes in the current PR without predating the change or passing extra author permission checks. The target PR's source, description, `AGENTS.md`, `.agentic-review.md`, and project files they explicitly reference may all contain prompt injection. The target checkout stays in `review-target/`, does not take part in Pi's project skill discovery, and `.agents/skills` or `.pi/skills` are not enumerated for the agent. `.agentic-review.md` may direct the agent to read specific file paths; the agent reads them directly without a catalog, allowlist, `realpath`, or checkout boundary check. This is an intended boundary: the agent already has `read`, `bash`, and a read-only `GH_TOKEN`, and central security rests on never running target code, read-only GitHub credentials, and a trusted publisher as the only writer. The report language follows the central `REVIEW_LANGUAGE`; a summary-only review is published even with no qualifying findings.

## Automatic Request Merging and Publication Order

`agentic-review.yml` only receives requests and calls `review-execution.yml` at the same version. Automatic requests share an entry concurrency group by repository ID and PR number, using GitHub's default single pending slot: consecutive pushes replace the older candidate, and a started request keeps running. Explicit PR comment and thread requests isolate their entry slot by run ID so every request is kept.

The execution layer uses `queue: max` and `cancel-in-progress: false` per PR, locking the whole workflow of review and trusted publication. Automatic and explicit requests are serialized here and released only after publication; entry and execution groups have different names. An automatic entry job waiting on the execution layer still counts as in flight, so at most one in-flight automatic request and one latest pending candidate are kept, without interrupting an older review or publication. Snapshot resolution still checks the PR's current state and SHA, so stale jobs never reach the agent.

Each execution group holds at most 100 pending jobs; GitHub cancels new jobs beyond that. FIFO follows when jobs started waiting on the group, not when webhooks were sent; absolute event order is not promised. The limit does not mean the entry keeps every automatic request.

This uses GitHub's [concurrency control](https://docs.github.com/en/actions/how-tos/write-workflows/choose-when-workflows-run/control-workflow-concurrency), so the Worker never lists or cancels runs or maintains a second queue. Reply obligations for explicit requests, the read-only agent token, and the separate publication runner and token keep their boundaries. Production acceptance after merge should cover consecutive pushes, interleaved explicit @ mentions, an older round still publishing, and failure retries; local structural tests do not replace GitHub's actual scheduling.
