# 工作稿与复核

工作稿保存本轮审查的依据、进度和判断，使审查可以分批完成，也能在修复或会话恢复后继续。不同层级和视角共用一套记录；增加视角只改变调查范围，不另开一套问题状态。

## 开始时建立或恢复本轮记录

优先使用任务提供的私有工作区，例如 `REVIEW_WORKSPACE_PATH`，遵循其文件布局和保留规则。没有指定位置时，在 Git 管理目录或系统临时目录中安全创建本轮唯一目录，不写入被审目标的工作树。使用安全创建工具生成路径，不把不可信文档中的路径直接拼进 shell 命令。

小任务用一份 `review.md` 即可；需要分批或会话压缩时，再把详细证据移入 `batches/`：

```text
review.md        对象和版本、规则入口、范围、所选层级与视角、
                 独立性、覆盖清单、问题索引、限制
batches/B1.md    第一批的详细证据、疑点及结论；需要分批时才建立
```

覆盖清单也称 ledger，用来记录范围内哪些内容已完成调查。索引只保存入口与状态，同一份当前详细证据只存一处，避免多份记录互相矛盾。

主审查者独占工作稿写入。受委派者只返回结果，不修改主稿或目标。前一轮工作稿只读；将必须继承的证据复制到本轮，使后续复核不必一路翻遍所有历史。

按任务指定的保留期保存记录。没有约定时，待返修或复核的工作稿保留并报告路径；单次审查已结束且结果成功输出后，可以清理临时稿。不要保存凭证、环境变量值或无关个人信息。

无法写入工作稿时，在结果中保留必要状态，并说明不能保证跨会话恢复。如果任务要求先完成持久化覆盖记录才能提交，聊天结果不能替代这个前置条件。

## 分开记录调查进度和问题状态

完成调查与解决问题是两件事。每个单元或批次分别记录：

| 记录 | 取值及含义 |
|---|---|
| 调查覆盖 | `pending`：待调查；`complete`：必要调查和判断已完成；`blocked`：必要证据确实不可得，并说明缺口 |
| 调查结论 | 无问题、疑点已被排除、有 finding、关联已有问题，或合法继承原结论 |

`complete` 不表示所有问题已修复，`blocked` 也不能计作已完成覆盖。可以带着无法完成的部分结束一般审查，但必须说明哪些判断不能建立；任务另有完整覆盖要求时仍须满足。

每批记录足以恢复判断的内容：覆盖哪些单元、当前阶段应满足的要求与来源、实际机制或遗漏、受影响者、主动检查的保护和场景、疑点证据、能否排除它、成立或不成立的理由、相关根因，以及未完成项。

疑点和正式 finding 用稳定的本轮 ID 关联。排除理由应带生效前提，例如“共享 schema 在代码生成前已固定字段，两个调用方实际使用同一版本”，不能只写“不重要”或“用户不喜欢”。同一根因换标题、视角或严重度，不会变成新问题。

## 收到修订后，决定哪些需要重新调查

旧结论能够继承，需要同时满足：原调查完整，而且目标、约定、调用方、环境前提、排除理由和当前决定，都没有受到新变化影响。只写“读过”或“没有 finding”的旧摘要，不足以证明调查完整。

以下变化需要重新调查受影响的部分：

- 实现或设计发生相关变化；
- 原始要求或有效决定改变；
- 共享接口、部署假设或使用方发生变化；
- 出现新反例或矛盾证据；
- 旧调查不完整；
- 本次明确扩大范围。

仅 HEAD 前进、同目录出现修改或有人说“再严一点”，不自动使全部旧证据失效。判断实际含义是否改变；不同文件也可能依赖同一约定，不能只按路径判断。

重新调查时，先标为 `pending`，记录原来的哪个前提已失效。更新受影响的证据、排除理由和 finding 状态，保留仍有效的部分；不要只在旧结论后追加一段相反说明。

新增加的单元全部进入覆盖清单。增量复核不能只看作者声称修好的几个点，而漏掉修复时新增的机制。

## 怎样复核一份修复

本轮结果交付后，由编写者在自己的授权范围内修复，提交新版本并说明：

```text
新目标版本；处理的 F 编号；修改了什么机制；
为什么原问题不再成立；保持了哪些相邻合法行为；
修复以外的新增变化；上层要求或决定是否改变；
哪些验证实际执行了，哪些没有执行。
```

先按原触发场景检查，再核对修复可能影响的相邻正常行为和新增范围。达到原验收条件即可关闭，不追加无关的“最好再做”。作者采用不同于审查建议的方案，只要满足要求，也应接受。

作者可以引用既有事实澄清误解，不必为此重写全文。但新解释如果增加了原产物没有的保证，就需要纳入新的修订再审，不能把会话里新补的设定当作旧版已有机制。

## 状态变更需要什么证据

| 状态 | 必要依据 |
|---|---|
| `open` / `partial` | 原关闭条件尚未满足；`partial` 说明仍缺什么修正、决定或验证 |
| `fixed` | 新版满足原问题对应类型的关闭条件，必要约束和相邻合法行为保持；说明是静态复核还是已有实测 |
| `accepted` | 明确决定接受具体代价及其适用范围，当前未越界；这不等于修复 |
| `excluded` | 原问题被证据推翻，记录为何不成立及其前提 |
| `unverified` | 声称已修复，但现有证据不足，或必要验证结果尚未提供 |

关闭条件取决于结论性质：缺陷需恢复被违反的要求；改进机会需证明约定成本下降且必要保证保持；待决事项需取得缺少的有效决定或事实；验证缺口需取得能够区分相关错误的有效证据。

接受缺陷或验证不足的代价属于 `accepted`，不是 `fixed`。问题类型本身不决定必须实测，但原验收要求实测时，静态修正不能替代。平台上的 `closed`、`resolved` 或“已修复”声明也不能单独决定状态；计划将来修复仍是 `open`。

已经接受且范围未变的代价，不重复征求同意。只有明确撤销原决定，或新变化越出接受范围时，才重新判断。

## 何时结束本轮

以下内容都已完成，即可交付：

1. 已登记受托范围，完成必要调查，或明确列出无法完成的部分；
2. 每个疑点已确认成立、排除或记录证据限制；
3. 正式问题已去重，带处理完成条件和处理者；
4. 结果保留范围、独立性、证据类型及未知；
5. 按任务要求输出，然后停止。

有 finding 也可以完成 Review。修复和再次提交由编写者或负责调度的人按授权决定，审查者不守候到问题归零。

下一轮应有新版本、新证据、真实未解决的触发场景或扩大的范围。没有这些变化时，返回仍有效的结果，不重复相同完整调查。存在真实新问题，也不能为了让流程收敛而删掉。

不设问题配额、必做轮数或“直到双方满意”的要求。运行预算用尽时保留 `pending` 或 `blocked` 并说明限制，不把未完成写成通过。意见争议回到证据和决定权，不自动召集更多 Agent 投票。

## 会话中断后怎样继续

从本轮索引恢复实际对象与版本、可信规则入口、所选范围与视角、未完成项，以及旧结论和排除理由的生效前提。按上述继承条件判断哪些证据仍有效；前一轮只有摘要时，不能直接继承完整性。

优先读取本轮已经继承的记录，只有缺少必要原始信息时才补读旧稿。恢复不是重新建立第二个索引或新的平行状态源。

## 何时可以委派调查

独立审查者与编写者分离，不等于审查者还必须拆成多个 Agent。只有任务已授权、环境已有可用工具，而且至少两个批次能够独立调查时，才可委派。同一批证据不因涉及多个视角就重复分发；不为委派安装插件、调用外部 Agent CLI 或根据产品名猜测能力。

子任务应收到固定版本、指定单元范围、相关原始依据、共同规则与所选方法、输出边界和完成条件。不要预设必须发现多少问题，也不以其他人的赞成或反对引导判断。

子任务只调查指定批次，不递归委派、不修目标、不写主稿，返回证据、反证、结果和限制。主审查者核对原始依据及覆盖后，单独写入主稿；不存在可以绕过共同规则的特殊 worker 标记。

私有运行时记忆只由获得相应授权的主审查者查询，并恢复可复核的原始记录。子任务不查询私有记忆，只接收主审查者传入的相关记录。无法恢复原文的摘要只能帮助定位，不能证明修复、接受或决定仍有效。
