# Review 证据

仅输出静态证据支持的高精度 finding，允许零 finding。

以下内容不构成 finding：

- CI 能稳定直接发现的格式、编译、类型或测试错误；
- 单纯缺少测试、覆盖率、注释、文档或 benchmark；
- 命名、布局、风格、抽象和架构偏好；
- anti-pattern、test smell 或危险代码形状本身；但 `test-contracts.md` 已静态证明 false verdict、assertion subsumption 或 zero-marginal signal 的情况除外；
- 没有真实路径、输入规模和成本差分的性能猜测；
- 必须依赖运行时 profile、压测或查询计划且静态代码无法证明的问题。

表面错误可由 CI 发现、但同一变更还有 CI 难以发现的生产风险时，只报告后者。

## Finding 接受判定

先证明候选，再判发布价值和严重度。本节只约束 P0/P1/P2 生产候选；T1/T2 和 `[需人工确认]` 使用专项门槛。

生产候选只有同时满足以下条件才能发布：

1. **归因**：问题由当前 diff 新引入、扩大或重新激活；
2. **可达**：存在由仓库代码和契约支持的现实入口与最小触发条件；
3. **违约**：head 的结果违反 PR 之前可独立恢复的产品、API、数据、安全、可靠性或操作契约；性能候选以 `performance.md` 证明的 base/head 成本退化和现实规模边界为准，不要求另有显式 SLA；
4. **实质影响**：差异会改变观察者得到的生产结果，或者改变其判断、下一步操作或故障恢复；仅仅能够观察到差异不足以发布；
5. **可操作**：能够绑定当前 diff 的根因位置并说明应恢复的约束；不要求给出唯一补丁，但必须说明需要修正什么。

生产结果包括成功或失败、返回值、状态、持久化、外部副作用、延迟和资源消耗，也包括错误代码、错误类别、失败对象、失败原因、修复指引、重试信号以及调用方据此作出的机器或人工决定。

诊断错报失败对象、原因、约束或修复方式，误分类为需要不同处理的错误，或丢失恢复必需的区分，均属实质影响。人工诊断须说明合理消费者会采取的错误操作、无效重试、重复提交或额外排查；机器信号须证明真实消费路径。“用户可能困惑”不足以成立。

保持错误类别、对象、约束和修复方向的等价改写，以及非必需的体验改进，不构成 finding。

最终状态、HTTP 状态码、是否拒绝输入或是否执行写入保持不变，只能反证这些特定维度，不能反证返回数据或诊断语义中的错误。

每个生产候选在 batch checkpoint 中记录：

```text
expected / actual / trigger / observer / substantive delta /
diff cause / strongest rebuttal / publish yes|no / failed gate /
severity P0|P1|P2|n/a
```

`substantive delta` 对结果错误记录生产结果差异，对诊断或恢复信号记录合理消费者的判断或恢复差异，对性能问题记录延迟、资源、容量或可靠性差异。`publish: no` 必须指出失败门槛并使用 `severity: n/a`；`publish: yes` 使用 `failed gate: none`，再根据影响确定严重度。严重度不参与候选真伪判断。

## 1. 建立 ledger 与 evidence batch

按 [`workspace.md`](workspace.md) 为完整变化集合的每个文件和非机械性 hunk 建立 change ledger，机械项注明理由。用 head 项目规则安排顺序，不缩小覆盖或降低门槛。

共享 base/head 文件、生产边界和独立契约的 ledger 项组成一个 **evidence batch**。batch 复用证据，不决定 finding 根因或去重；小 diff 证据相同时只建一批，不按章节、候选数或 cluster 拆回合。

删除、修改和新增代码同等检查；测试断言、校验、过滤、权限、默认值、错误分支、事务、重试、清理、批处理、分页和缓存的删除或放宽不能因改动小而跳过。

## 2. 每个 batch 单遍完成行为证明

读取 batch 的 patch，补齐 ledger 中的非机械性 hunk，再读取改动所需的源码上下文和最小直接依赖。小 diff 已一次读完时直接复用；大 diff 逐文件读取，大 patch 和大文件按行区间读取，每段证据与覆盖进度落盘后继续，直到当前 batch 的变化全部覆盖；截断不视为已读。在进入下一批前完成以下维度：

1. **行为差分**：哪些输入、身份、状态、规模或调用顺序现在得到不同处理；最终读取、写入、返回、发布、删除、分配或调用什么。
2. **独立契约**：从生产代码、数据库约束和迁移、API/事件/任务契约、调用方、被调用方、持久化格式、消费者、稳定文档和 base 行为恢复约束。当前变化新增或修改的测试、文档、schema、配置或注释不能单独为同一变化背书。
3. **真实路径**：有限追踪 `入口 → 校验与转换 → 核心决策 → 持久化、外部副作用或资源消耗 → 返回、错误、重试或清理`，达到足以判断结果的稳定边界，不无边界扫描仓库。
4. **观察者与成本**：哪些调用方、租户、数据、消费者、外部系统或资源预算会观察到差异；工作量是否随集合、分页、重试、外部往返或并发变化。

生产代码与测试、fixture、snapshot、mock、helper 或 CI 配置同时变化时，分别确认生产行为、断言依据、断言是否放宽、mock 是否绕过真实边界，以及 expected 是否与实现共享真相源。

重试、降级、冲突恢复、并行化和补偿路径应保持同一个逻辑操作。没有独立授权或当前 PR 明确确认回复时，恢复路径不能为了成功而静默改写租户、业务日期、资源范围、资源身份、幂等键、顺序或业务载荷。数据库约束仍满足、操作最终成功或测试同步更新都不能证明语义等价。

证据已在上下文时引用 batch 记录；仅因候选复核、证据冲突、文件变化或 compact 后无法准确恢复而重读。

## 3. 在 batch 内按触发进入专项

先完成主行为路径，再对 batch 内匹配项进入专项：

- 成本随集合、分页、载荷、并发、锁、事务、重试或外部往返变化时，完整读取并执行 [`performance.md`](performance.md)；
- 当前变化改动测试、fixture、snapshot、mock、test helper，或生产变更使既有测试错误判定重新可达时，完整读取并执行 [`test-contracts.md`](test-contracts.md)。

机械变化不加载专项。专项结论写回当前 batch，不另起一次全 diff 扫描。

## 4. 候选就地构造反例并独立反证

只对有现实触发依据的候选构造能区分 base 与 head 的最小输入、状态、规模或调用顺序。覆盖与改动相关的空值、边界、重复、乱序、异常、部分成功、重试、补偿、终态、权限、租户、持久化和消费者；测试与性能候选使用专项规则。

在当前 batch 记录独立反证，核对候选的精确 base/head 行及契约：

- 上游校验、下游保护和合法例外；
- helper 已有分页、批处理、缓存、去重或惰性执行；
- 顺序、精确值、调用次数或完整集合是否属于外部契约；
- 输入规模是否被静态限制为小常数；
- 替代机制是否保持权限、顺序、事务、失败和返回语义；
- base 是否已有相同失败或成本；
- 当前变化是否确实引入、扩大或重新激活问题；
- 调用方提供的已有 Review 或问题记录是否已覆盖同一根因。

候选被反证后记录排除理由，结束其证明。

## 5. 按需查询 known issue

候选通过代码与契约反证后，只有已有记录可能改变业务授权、归因、严重度、去重或当前状态时，才读取 [`known-issues.md`](known-issues.md)。查询入口限于调用方提供的关联索引、当前审查输入中的明确稳定引用，以及受信任本地环境可恢复的持久记忆；没有入口就结束 known issue 判断。索引标题和宽泛主题相似本身不足以读取记录。

## 6. 检查高风险契约变更

认证授权、租户隔离、资源归属、敏感信息、数据删除迁移、唯一性、事务、业务日期、金额、状态、幂等、重试补偿、API/事件/持久化兼容，以及数据规模、分页、批量、并发、超时、速率、重试预算和资源配额的放宽，都要检查是否需要人工确认。

- 已证明具体生产错误或性能后果：使用 P0/P1/P2；
- 确实改变高风险边界，但审查时既无独立授权、迁移、容量或兼容性依据，也无当前 PR 明确确认回复：使用 `[需人工确认]`；
- 同一根因的 P、T 和 `[需人工确认]` 互斥，保留最接近真实影响且证据最强的一条。

## 7. 完成 batch 并最终归因

按 `workspace.md` 完成覆盖状态与 batch 记录；每个生产候选填写接受判定。未 complete 的 batch 不进入最终归纳。

全部 batch complete 后按 `findings.md` 归因去重，同一成本放大的延迟、配额和账单影响合并为一条；最终归纳的重读条件见 `workspace.md`。
