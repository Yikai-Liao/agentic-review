# 共同调查方法

各层审查都从同一个问题开始：依据用户目标和相关约定，当前产物是否合理，哪些问题需要现在处理？本文件说明如何建立依据、完成调查和验证疑点；具体检查方法由所选层级和视角提供。

已有证据可以复用。以下要求用于判断调查是否充分，不要求每发现一个疑点就重新读取全部材料或执行一遍所有步骤。

## 固定本次审查的对象和范围

先记录要审的对象及其版本。代码可以用 commit，文档可以用修订号、保存的正文或内容哈希；目的都是让后续人员能恢复同一份材料。目标更新时，可以完成原版本的调查，也可以重新调查受影响的部分，但不能把两个版本的证据拼成同一个结论。

区分两种范围：

- **增量审查（delta）**：检查本次引入、扩大或重新触发的问题，以及新提案本次准备确定的内容。报告时说明它与当前变化的关系。
- **整体审计（audit）**：检查明确指定范围的当前状态，可以报告其中已有的问题，但不能声称这些问题由本次变化引入。

同时明确当前要作出的决定或交付、所选层级与视角、原始依据、权限、输出要求和可用的历史记录。新提案没有旧版本并不妨碍审查，原始目标仍可提供判断依据。已有信息足够的部分继续调查；只有信息缺口会改变判断时才询问，不擅自扩成全仓库审计。

## 先查清当前阶段需要满足什么

这里要分清三个问题：预期依据什么、哪些要求现在就要落实，以及尚未确定的内容会影响什么。文档与代码一致，只能回答它们是否采用了同一种做法，不能替代这三个判断。

### 找到独立于待审产物的依据

先读用户原话、有效决定和实际使用场景，再查相关接口、数据约定及已有系统的基线。这些有明确依据、产物需要遵守的行为约定称为**契约**，例如调用条件、返回结果或数据保留要求。实际调用方的使用方式也可能提供必要依据。

这些材料提供了独立于待审产物的判断依据。已有代码可以说明系统现在怎样工作，却不能单独证明它应该这样工作；同期新增的代码、测试和注释彼此一致，也不能互相证明正确。作者摘要用于定位材料，不是唯一依据。审查需求本身时，直接从原始诉求和实际场景判断，不要求用户先交出另一份完美需求。

**独立依据不等于更早的依据。** 当前明确的业务决定可以改变预期，是否有效按任务给定的来源规则判断。来源发生冲突时，并列原文和适用范围，说明不同解释会造成什么实际后果；不要仅因某份文件层级更高就认定它一定正确。

相关历史记录也可能补充依据，或改变原问题的状态。此时按[关联记录与既有问题](known-issues.md)，沿任务允许的入口、稳定引用或获授权的记忆取得原文，核对实际关系并决定本轮如何处理。只读取会影响预期、本次变化归因或问题状态的记录。标题、摘要和 `closed`、`resolved` 等标签，只能用来定位材料，不能单独证明风险已被接受或问题已经修复。

### 判断哪些要求现在必须落实

对每项相关要求，查清谁在什么条件下需要什么结果、由谁负责，以及最晚应在什么阶段落实。判断的关键是：当前准备作出的决定或交付，是否已经依赖这个答案？已经需要确定的要求，与仍可自由选择的实现细节，要分开处理。

例如，一个计划先安排接口能力调查，再根据结果选择方案。调查结论尚未产生，不意味着计划有缺陷；但如果计划要求先执行不可逆的数据迁移，最后才确认迁移依赖的接口能力，就需要检查这个顺序是否让当前交付依赖未经确认的条件。是否必须现在知道答案，取决于后续工作是否已经依赖它。

### 将未知落实为具体的判断限制

记录时区分原文支持的事实、据此作出的推演和仍然未知的部分。目标有缺口时，说明缺什么以及它会改变哪项选择：能够继续读取资料解决的，先调查；需要用户取舍的，保留具体问题；合法留待后续的，不提前判错。不要替用户发明指标、优先级、攻击者能力或未来需求。

## 调查全部受托内容及必要连接

将受托范围划成能够分别作出判断的单元，例如一项需求、一个接口、一段状态变化或一组相关代码。包括新增、修改、删除、放宽限制和责任转移，也从目标反查作者没有列出的工作。

依赖相同机制和原始依据的单元，可以放在同一**调查批次（batch）**中，共享读取结果；小任务一批即可。分批是为了复用证据和保留进度，不代表同一批的所有问题都有相同根因。

先理解当前方案怎样工作，再用相关场景检查它。对每个单元，需要能说明：

1. 当前阶段应满足什么要求，依据是什么；
2. 产物用什么规定或机制满足它，或者缺少哪个必要环节；
3. 哪种实际场景、输入、顺序、修改任务或验收结果能够检验它；
4. 谁会观察到什么实质影响；
5. 已检查哪些保护，哪些选择本来允许，哪些部分仍缺证据。

新增、修改或依赖的保护也要主动调查。例如，增加重试机制后，应检查相关失败顺序是否保持原操作的语义，而不是等到看见明显可疑代码才追踪。各层方法提供具体做法；相同机制已有充分证据时直接复用，不重复全量扫描。

风险排序只改变调查顺序，不取消受托范围。完成调查意味着每个相关单元都有结论，不意味着穷举所有可能输入或执行全部专项。机械性变更可以注明无需进一步分析的理由；范围外的内容不能标为已审。

必要路径仍可读取时继续追踪，不能用“证据不足”提前结束。资料确实不可得时，记录缺什么、尝试过什么、限制了哪个判断；没见到材料不等于机制不存在。窄审中偶然发现范围外的重大问题，可以单独提示，但应说明没有扩大审查覆盖。

## 验证疑点并形成结论

疑点是尚待证明的可能问题。按[结论的证据要求](findings.md)判断它是否成立，再使用所选方法补足领域证据。定位最先不满足要求的规定、机制或遗漏，说明后果，不从一个缺口派生多条同根因问题。

主动寻找能够推翻疑点的解释，这一步称为**反证检查**。优先检查最有可能使当前判断失效的情况：上下游保护、真实输入限制、已分配的后续决定、已接受的代价、旧版本本就存在的问题，以及替代方案带来的成本。排除疑点时保存理由和生效前提，不换标题或类别重新报告；没有找到保护，也不等于已经证明没有保护。

证明成立后再判断严重度。潜在影响很大不能免除证据要求，每个疑点最终都应得到成立、排除或受限的明确处理。多个视角发现同一根因时合并；需要改变上层目标或决定时，保留具体反例并交还给有权决定的人。

输出前检查受托覆盖、疑点处理、处理完成条件和未知是否清楚。按结论要求交付后结束；返修、历史继承和会话恢复使用[工作稿与复核](review-state.md)，不另建一套状态记录。
