# 需求审查：理解并完善要做什么

需求审查关注用户、场景、目标、约束、范围、例外和验收。它既检查整理后的需求是否忠实于用户，也寻找需要澄清的遗漏、矛盾和取舍；不要求这个阶段就写出完整架构或实现。

判断依据来自用户原话、实际场景、外部约束和明确决定。原始诉求含糊时，指出哪些选择会改变结果，而不是替用户发明偏好。

## 选择本次要检查的内容

普通需求审查使用表中标为“默认”的方法，围绕受影响的要求选择场景；标为“明确委托”的专项不自动加入。明确“只审某项”时，仅检查该项及必要依据，不因为读取了本文件就宣称所有专项已经完成。

| 检查内容 | 方法 | 何时使用 |
|---|---|---|
| 是否忠实表达意图和范围 | [意图对齐](../focuses/alignment.md)及下文场景检查 | 默认 |
| 要求之间是否冲突，取舍是否明确 | 下文一致性检查 | 默认 |
| 验收是否会接受错误的结果 | [验证](../focuses/verification.md)中的验收有效性方法及下文例子 | 默认；不要求现在就完成实测 |
| 假设和决定是否足以支持下一步 | 下文假设检查 | 默认 |
| 是否增加了不必要的实现约束 | 下文方案约束检查 | 明确委托：要求简化或审计约束成本时 |

`simplify` 在本层检查不必要的方案约束，不删减用户目标。`harden` 检查实际相关的例外、保证、验收和必要决定，不凭空增加故障清单。明确审安全需求时，用场景和一致性方法检查身份、资源以及允许或禁止的操作，不能凭需求文档证明实现已经安全。

## 先明确当前需要确定什么

登记受影响的用户结果、场景、约束、范围决定和验收，并从原始诉求反查遗漏。区分用户需要、作者假设、拟作出的决定，以及已经有效的决定。

探索阶段可以保留待验证假设，但要能够说明什么证据会改变选择、何时必须知道答案。准备确定范围或移交实施时，影响目标和验收的选择不能无人负责。

技术方案、接口格式和内部实现通常留待后续阶段决定；它们本身已经是外部约束时，才属于当前需求。不要把合法的阶段分工报成遗漏。

## 检查意图和范围是否走样

按[意图对齐](../focuses/alignment.md)，比较用户原始场景与需求中的适用条件。重点看不同用户、时间、身份、历史数据及例外是否仍得到支持，定位到具体条款或范围决定，而不是假定已有实现路径。

例如，用户要求离线也能记录，整理稿却只承诺在线提交。无网络的真实使用场景说明目标被排除了。提出问题前，核对用户是否已明确同意本期只支持在线，或是否有另一个已纳入交付的机制承担离线记录。若有，就按实际批准范围判断，不恢复用户已经放弃的目标。

## 检查同一场景下的要求是否冲突

尝试找出一个合法场景，使两项要求必须给出互相冲突的结果。核实它们是否作用于同一对象、时间和条件；不同角色或不同阶段使用不同规则，不自动构成矛盾。

例如，同一数据既要求到期后不可恢复地删除，又要求删除后任意时刻恢复原内容，两项要求在相同范围内无法同时满足。若实际只要求删除在线副本，并明确允许限期保留备份，则要按这个约定判断，不能擅自加上更严格的删除含义。

已经确定的要求互相冲突，可以形成缺陷（defect）。文档只是列出互斥选项让用户选择，并不等于承诺同时实现；只有下一步已经依赖选择结果时，才作为待决事项（decision），说明谁需要决定什么代价。

## 检查验收是否能排除错误结果

验收有效性关注：能否构造一个通过全部验收，却没有满足用户目标的产物。本层可以用假想产物推演，不要求存在可运行测试。方法见[验证说明](../focuses/verification.md)。

例如，目标是“操作失败后，用户知道下一步如何处理”，验收却只要求显示一条消息。始终显示“操作失败”也能通过验收，却不能让用户区分应该重试还是修正输入。只有原始目标确实需要这一区分时，问题才成立；处理目标是补足必要的行为区分，而不是现在指定 HTTP 状态码或界面实现。

也要检查相反情况：验收是否拒绝了本来满足目标的结果。精确文案、页面数或工具名称可能来自品牌、法规、无障碍等真实约束，不能因为它看起来像实现偏好就要求删掉。

具体的错误验收按缺陷证明。如果本次是在审查“当前应取得的验证证据是否足够”，则按验证缺口（verification-gap）的独立要求判断，不能把所有尚无测试的需求都视为缺陷。

## 检查假设是否足以支持下一步

分开看事实、产品假说和价值选择。说明哪项后续投入或范围决定依赖未知，不同答案会怎样改变目标或验收。已有资料能够回答的先读取，不把普通调查转交用户。

例如，计划确定范围时假定“所有目标客户都能联网”，但已有用户场景包含离线人员，应先处理事实冲突。只有目标用户群本身尚未确定，而且选择会改变本期目标时，才返回最小需要决定的问题。

“先访谈验证，再决定范围”是合理的探索安排，不能因为现在还没有调查结果就阻止已获授权的探索。

## 检查是否规定了不必要的实现方案

只有明确委托简化或成本审计时，才使用这一方法。选取真实的交付或需求修订任务，说明某项实现规定没有独立目标依据，却增加已知成本，或排除了能够保持目标的低成本方案。

例如，只需导出标准文件，却规定必须建设专用编辑器。如果现有导出能力已满足全部确认目标，而编辑器带来额外交付责任，可以提出改进机会（improvement）。若用户确实需要编辑器内的交互，则替代方案没有保持目标，不能用它证明约束多余。

给出可行替代及迁移、沟通代价，不能只说“需求不该写技术”。不以代码行数或抽象层数衡量需求，也不能为了简单就移除合法使用场景。删除冲突要求前，仍需要有权者决定。

## 交付和复核

按[结论要求](../findings.md)，每条问题保留原始依据、条款或遗漏位置、具体场景、已核对的合理解释、处理者和完成条件。未知仍写未知，不替用户决定偏好。

处理完成可以是恢复目标、补足验收区分、取得明确且有范围的决定，或证据推翻了原疑点。目标不是让需求更长或全部量化。本轮完成的是受托需求审查，不证明后续设计、实现或产品价值已经验证。
