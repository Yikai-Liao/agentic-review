# Requirements：审查是否正确决定了要做什么

对象是用户、场景、目标、约束、范围、例外、成功条件与业务分叉，不是尚未展开的架构。独立依据来自用户原话、已有实际场景、外部约束和明确决定，不要求再有一份完美的上级需求。原始诉求含糊时不能替用户发明偏好。

## 侧重点与范围

未限定时检查下表前四项，按受影响承诺取样；明确窄审只调查所选项及必要依据。读本文件不意味着所有专项都已完成。

## 范围单元与当前成熟度

为受影响的用户结果、场景分区、约束、范围决定与验收建立单元，并从原始诉求反查遗漏。区分用户需要、作者假设、拟作决定与已经有效的决定。

探索阶段可留下待验证假设，但应能知道什么证据会改变选择、何时必须得到答案。准备承诺范围或移交实施时，影响目标和验收的分叉不能无责任地留下。技术方案、接口格式和私有实现细节通常不在本层到期，除非本身就是外部约束。

## 意图与范围保真

按意图对齐方法，需求层主要比较用户、时间、身份、历史数据与例外的场景分区，定位条款或范围决定，不假设已有实现路径。

例：用户要求离线也能记录，整理稿仅承诺在线提交；给出无网络的真实使用场景，说明目标被排除。反证是用户已明确批准本期仅在线，或另一个已纳入交付的机制承担离线记录。范围决定存在时尊重它，不恢复被明确放弃的目标。

## 一致性与取舍

构造同一合法场景下两项承诺要求相互冲突结果的最小实例；说明是否真在相同时间、对象和适用条件下。不同角色或阶段适用不同规则不自动冲突。

例如同一数据既要求到期不可恢复删除，又要求删除后任意时刻恢复原内容；若范围确实重叠，可证明矛盾。若要求仅删除在线副本并明确允许限期备份，则必须按实际承诺判断，不擅自加严格删除语义。

已明确冲突可为 defect；保留多个互斥选项待用户选择不等于已承诺两者。只有下一步确实依赖该分叉时才形成 decision，说明谁决定什么代价。

## 验收是否排除了错误产物

使用验证特化的错误验收见证。本层观察的是用户行动、判断和下一步结果，证据可以是假想但满足全部验收的产物，不要求可运行测试。

原始目标是“失败后知道下一步如何处理”，验收只要求显示一条消息。始终显示“操作失败”满足验收，却不能区分重试与修正输入；只有独立目标确实要求这一区分时才成立。关闭是补上必要行为区分，不要求现在确定 HTTP 状态码或 UI 实现。

本层的允许变化反证尤其包括品牌、法规、无障碍等真实约束；不能因为精确文案、页面数或工具名称看起来像实现偏好就删除它们。

具体错误验收按 defect 证明。若审查的是已经到期的验证证据能否支撑承诺，则按 verification-gap 门槛，不把所有尚无测试的需求判为未验证缺陷。

## 假设与决定是否足以支撑下一步

区分事实、产品假说与价值选择。证明哪个下一步投入或承诺依赖未知，以及不同答案将如何改变范围/验收。已有来源可直接回答的先查，不把普通调查转给用户。

例如范围承诺依赖“所有目标客户都可以联网”，但明确用户场景包含离线人员；优先处理事实冲突。只有用户群尚未确定且选择会改变本期目标时，返回最小业务决定。合法的“先访谈验证、再决定范围”不是缺陷，不能因没有调查结果阻止获授权探索。

## 不必要的方案约束

仅在明确委托时，选择一个真实交付或需求修订任务，证明某项实现规定没有独立目标依据，却增加已知成本或排除保持目标的低成本方案。给出可行替代及迁移/沟通代价，不能只说“需求不该写技术”。

例：仅需导出标准文件，却新增必须建设专用编辑器的规定；现有导出能力满足全部已确认目标，编辑器带来具体额外交付责任。可报告 improvement；若用户明确需要编辑器中的交互，替代不保持目标，应排除。

不要用代码层的行数、抽象层数衡量需求；删去冲突条款前需要有权者决定，不能为了让需求简单而移除合法场景。

## 成立、关闭与反馈

共同门槛见 [结论契约](../findings.md)。每项见证有原始依据、条款/遗漏位置、实际场景、最强反证、处理者和关闭条件。未知保留为未知，不替用户决定偏好。

关闭可以是恢复目标、补齐必要区分、得到有范围的明确决定，或反证旧怀疑；不以文档更长或需求全部量化为目标。本轮完成的是受托需求审查，不证明后续设计、实现或产品价值已经验证。
