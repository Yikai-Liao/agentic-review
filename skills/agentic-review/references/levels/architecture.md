# Architecture：审查设计能否承接意图并约束协作

依据用户需要、现有承诺和当前被审方案工作，不规定微服务、数据库或设计风格。C4 式层级与使用设计只是表达/调查方法，不要求图集、会议或固定场景数。共同证据与结论规则从 Skill 入口按需加载，本文件只定义架构判断。

## 侧重点与加载

未限定时调查前五项中与当前承诺相关的部分；明确窄审只执行所选方法及必要依赖。先确定被审对象；场景演练用于调查相关场景，不是额外一轮全量审查。

| 侧重点 | 方法/特化 | 选择 |
|---|---|---|
| 目标承接 | [意图对齐](../focuses/alignment.md) + [意图与目标承接](#意图与目标承接) | 默认 |
| 边界与组合正确性 | [组合正确性](#边界与组合正确性)与[场景演练](#场景演练) | 默认 |
| 状态与失败责任 | [可靠性](../focuses/reliability.md) + [状态与失败责任](#状态与失败责任) | 默认核对实际承诺，不扩大故障范围 |
| 演进与兼容 | [演进与兼容](#演进与兼容) | 既有系统变化时 |
| 关键理由与决定 | [理由与决定](#理由与决定) | 影响本次决定时 |
| 变更与协作成本 | [可维护性](../focuses/maintainability.md) | 明确成本/简化审计时 |
| 信任与隔离边界 | [安全](../focuses/security.md) | 明确安全审查或改变安全边界时 |
| 验证充分性 | [验证](../focuses/verification.md) | 明确验证审计或当前验证义务到期时 |

simplify 映射变更与协作成本；harden 映射状态/失败责任与验证充分性。它们不扩大到无关边界，也不要求设计探索提前取得上线验证。容量约束用当前规模和可行机制调查，不套代码 diff 的性能标签；只因没 benchmark 不成立。

## 确定这次在审什么

区分当前实现、已批准目标、本次提案与历史理由。读取相关原始需求、现行边界、有效决定、提案增量和实际依赖；不为理解一个局部变化重建全项目。

新设计没有代码和 base 时仍可审独立目标与设计机制。代码存在时用于核对基线事实，不用现有代码反向制造用户需求。被审设计中的批准字段不能自行授权。

登记受影响的能力、关键决定、责任/状态/外部契约和它们之间必要的连接。先系统边界，再进入涉及的服务/模块内部；不要把部署单元、内部函数和业务目标平铺成同级检查项。不强迫作者重画图，能引用清楚的文字就使用文字。

## 意图与目标承接

使用意图对齐方法，将原始目标分区映射到设计承担者及机制。本层需区分身份、历史数据、恢复、阶段、子对象和消费者；职责名称或连线存在不证明目标已被承接。

例：原始要求“执行开始后，后续配置变更不影响该次执行”；方案只冻结主定义但运行时仍解析可变子定义。证明子定义的变化如何改变当前执行，才报告；不凭“快照”二字要求冻结所有世界状态。

反证：需求明确只要求主定义、子定义本来是不可变引用，或该行为已被明确接受。命中就排除。

## 边界与组合正确性

对实际需要共同完成一个目标的两个下级单元，尝试构造：

```text
单元甲遵守全部已给约束 → 行为甲
单元乙遵守全部已给约束 → 行为乙
二者在真实共享边界组合 → 无法满足哪个上级承诺
```

核对共享标识、字段含义、状态写入权、顺序、生命周期与失败责任。下级单元可以是模块、服务、迁移批次或并行开发任务，不默认是两个 Agent。

**不是所有不同实现都必须统一。** 以下不接受：单元根本不交互；差异已被适配器隔离；共享契约将在共同拆分前由已指定责任人确定；内部数据结构不同但外部语义一致。

已有约束明确冲突并有违约时用 defect。当前马上要独立实施，却没有任何共同机制决定必要边界时，可用 decision 指出最小需要统一的内容。尚未到期的内部选择不升级为设计问题；不要求把所有自由度写死。

## 场景演练

从真实目标/消费者选择能区分方案的场景，沿材料已有机制逐步使用设计：入口、责任、持久状态、对外承诺、观察者结果。每一步标明依据；不要让设计作者现场补设定使旧版自洽。

卡住后依次检查：

1. 是否已有跨文件引用或现行契约可以补齐？先读。
2. 是否是本阶段合法省略且已分配的实现细节？不报。
3. 是否是当前承诺必要的机制或关键决定缺失？按 defect/decision 门槛判断。
4. 是否仅因审查者不熟悉术语？查明术语，不转成作者整改义务。

“first blocking point”只是定位手段，不意味着卡住即阻断。只报告具有当前实质影响的缺口，并保持“未定义”与“已证明错误”的区别。

## 状态与失败责任

使用可靠性特化的失败时序与恢复见证。架构层应以已写明或现行契约提供的责任、持久事实和机制推演，不能靠作者现场补充新设定使旧版自洽。没有实现不妨碍静态设计矛盾成立，但缺少本阶段合法委派的私有细节不证明失败。

方案明确违反保证时可直接 defect；机制仅依赖未证实的外部能力，而下一承诺马上依赖它时才考虑 decision。成本主张用真实规模、路径和上下界；不能以技术名称或“工业级”证明容量，也不能因为没有 benchmark 一律阻断。

## 演进与兼容

已有系统变更要区分 old、允许的中间态和 target。按实际部署/数据演化边界推演新旧参与者共同存在的阶段、已有数据与迁移结果、回退承诺。只审相关组合，不遍历不受支持的版本。

另一活动变更触及同一主题只是线索；必须指出共享前提怎样改变才要求协调。纯提案不能写成当前已经上线；一个 PR 完成不代表跨 PR 目标全部交付。

## 理由与决定

对影响边界、代价或后续投入的重要选择，核对“为什么”是否来自事实，还是作者把猜测写成事实。必要时比较最有竞争力的可行替代，但不为每个选择强制列三种方案。

只有错误前提/缺证据会改变当前选择时才报告；材料没有叙述全部理由不等于技术选择错误。用户尚未决定的价值取舍以 decision 返回；已接受且未越界的代价不重复挑战。

## 记录与完成

每批记：独立义务 → 所在层级/承担者 → 场景或组合 → 路径与依据 → 反例/第一个必要缺口 → 反证 → 当前处理者与关闭条件。

全部受影响承诺、必要连接、重要决定都有调查结论，当前阶段合理省略已区分，才能完成受托范围。上交用户的是仍需要权衡的决定及关键残余风险，不是完整审查日志。结论是“在明确范围与证据下未发现需处理问题”，不是架构正确性证明。
