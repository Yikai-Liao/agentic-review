# 性能：证明真实且可避免的成本放大

性能审查关心实际路径在现实规模下是否付出了显著、可避免的额外成本。循环、并发或缓存变化只是调查线索，不是问题证据。

增量审查（delta）比较修改前后，即 base/head；整体审计（audit）比较当前路径与保持行为的可行替代，不能伪造一个旧版本。下文的“对照成本”分别指旧版或替代方案。

## 建立能够核对的成本模型

先查清每次操作花费什么，以及它会重复多少次。可按实际路径组合以下因素，不要求精确预测毫秒：

```text
执行频率 × 单次操作成本 × 分页或集合规模 × 重试、补偿等放大因素
```

单次成本可能是 CPU、内存分配、拷贝或序列化的字节、远程往返、锁持有时间。模型必须说明：

- N、M、页数、批大小、载荷、并发或重试次数各指什么；
- 规模来自实际调用方、数据结构约束、API 上限、分页配置、租户数据还是已有代码；
- 当前和对照的操作次数、复杂度、内存峰值或外部往返；
- 哪条真实调用路径承担这些成本。

例如，实际请求要读取一万个 ID，现有 API 能按一千个一批等价读取。由十次批量调用改成一万次逐项调用，才能给出具体差异；仅说“循环里调用 API 可能慢”不够。

## 从变化中寻找值得建模的路径

以下变化需要沿真实路径调查，但不直接决定 finding：

- 嵌套线性扫描，或循环中重复排序、聚合、解析、编译、序列化、解压和拷贝；
- 每个元素单独调用数据库、GraphQL、REST、对象存储、Redis 或 RPC；
- 拉取全部数据后才在客户端过滤、去重或分页；
- 流式处理变成一次性把全部内容放入内存，或反复复制不断增长的 buffer；
- 有界批处理变成无界并发任务，例如 `Promise.all`、goroutine 或线程；
- 外部 I/O 进入事务、全局锁、租户锁或关键请求线程；
- 单项重试变成整批重做，或多层重试相乘；
- 同一路径重复查询、转换或读取大对象；
- 失去缓存、去重、分页、短路、索引选择性或在数据源先过滤的能力；
- 异步、离线或按需工作进入同步高频路径。

## 什么程度的成本问题可以报告

性能 finding 需要同时满足三方面：真实成本达到下列报告门槛、有保持行为的低成本替代，以及成本会造成具体影响。只满足其中一方面不够。

### 真实成本至少符合以下一项

1. 输入不是静态小常数，复杂度相对对照恶化一个阶，例如 `O(N)` 变为 `O(N²)`。
2. 数据库或远程往返从常数或批量调用，变成逐项、两层集合相乘或嵌套分页。
3. 在仓库支持的现实上限或常见规模下，静态下界已证明 CPU、调用、传输、分配或内存峰值放大约一个数量级。
4. 单个请求可触发无界并发、全量内存展开、队列增长或资源耗尽。
5. 外部等待显著延长事务或锁持有时间，形成明确的连接池、锁竞争或吞吐限制。
6. 重试、超时或部分成功会成倍重放同一批工作或外部副作用。

### 存在保持行为的低成本替代

指出一条当前可行的低成本路径，例如旧有机制、标准数据结构，或当前依赖和服务已经提供的能力。证明它保持权限、顺序、事务、错误和返回行为；如果节省成本必须牺牲这些保证，就不能据此认定当前成本可以避免。

### 说明实际影响和根因

结合前面已核实的触发规模，说明请求数、延迟下界、限流、内存、连接占用、队列或账单等后果，并定位所审版本的最小根因行范围。

“数据大时可能慢”没有达到上述要求。

## 核对是否存在合理成本

报告前检查：

- 输入是否已被类型、结构校验或调用方限制为很小的常数；
- 路径是否只是一次性迁移、离线维护或极低频管理操作；
- 辅助函数或 SDK 是否已有批处理、连接复用、缓存、分页或并发控制；
- 批量 API 是否改变授权、原子性、顺序、配额或失败行为；
- 顺序执行是否来自限流、幂等、锁或外部协议的必要约束；
- 当前是否用有界并发换取更低延迟；
- 对照是否已有相同数量级成本；
- 替代算法是否改变输出稳定性或边界行为。

任一项能推翻“显著且可避免”，就排除该疑点。

## 交付和复核

性能问题使用[代码 P0/P1/P2 标签](../code.md)。复杂度符号本身不决定严重度；现实规模、频率、单步成本、并发和实际影响才决定。

每个受托性能单元都应有当前与对照的成本模型、规模依据、替代机制和反证结论，最终说明无 finding 或成立的级别。复核时重新检查原成本差异和行为保持，不能只凭换了数据结构就宣布修复。
