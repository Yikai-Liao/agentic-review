# 测试审查：判得准，并保留有价值的检测

测试审查不是统计测试数量，也不是看到两段测试相似就删掉一段。我们检查测试是否按真实要求作出判断，以及它能否发现其余测试发现不了的真实错误——这称为独立检测能力。

这里的**契约**指有独立依据、测试负责验证的行为约定。生产代码和测试互相使用同一个错误常量，即使测试通过，也不能证明契约得到满足。

## 选择本次范围和问题类型

增量审查（delta）包含本次修改的测试用例、参数行、断言、测试数据（fixture）、快照（snapshot）、模拟对象（mock）和测试辅助函数（helper）；也包含生产变化使原有错误测试判定重新可达的情况。整体审计（audit）针对明确委托的当前测试集合，报告时注明问题已有，不伪造新增归因。

不报告单纯缺测试、覆盖率或用例。测试审查有三种不同问题：

| 类型 | 要证明什么 |
|---|---|
| **T1：测试失真（false confidence）** | 测试放过了它本来应发现的错误 |
| **T2：测试过约束（change detector）** | 测试拒绝了契约允许的合法变化 |
| **T2：冗余测试信号（zero-marginal）** | 测试可能判得正确，但相对其余测试没有新增错误检测能力，只增加重复失败信号或维护点 |

前两种属于测试有效性，第三种属于测试经济性。完整代码审查按下文变化表选择分支；明确窄审只执行受托分支及其必需证据，其他部分标为范围外，不宣称已经审过。

三种方法共用盘点和分析结果，不各自重扫全部测试，也不另建工作稿、状态或输出流程。

## 先盘点变化，再按测试含义分组

先为范围内每个用例、参数行、断言、快照、测试数据、模拟对象和辅助函数分配稳定的盘点编号，记录为 **census ID**。同一个测试里，每条发生变化的断言都要分别登记。

每项记录位置、类型、受影响的测试，以及它属于哪些分组和调查批次。这样才能发现遗漏，而不只是审查几个看起来可疑的测试。

分组有两个层次：

- **按职责分组（contract family）**：同组测试负责验证同一行为约定，位于相同生产边界和测试层级。它只共享这些依据，不代表测试可以互相替代。
- **按语义特征分组（contract fingerprint）**：在上述组内，进一步比较输入类别、边界、生产路径、预期与判定路径、可发现的错误和风险维度。任一项不同就分开，不能因文件或测试名相似归为相同语义。

依赖相同修改前后代码及原始约定的分组，可以放在同一**调查批次（evidence batch）**中，一次读取后复用。一个批次可以包含多个职责和多个问题根因，不代表它们应该合成一条 finding。

测试数据、mock 或 helper 可能影响多个分组或批次。每条 `census item → fingerprint` 关联都须有调查结论，不能只给这个共享文件写一个总状态。

## 为每批建立可比较的证据

增量审查对照 base/head；整体审计比较当前成员与准备保留的测试，不声称存在旧版本。只读取所选分支需要的相关代码和契约，一批内共享，不多轮扫描全套测试。

职责层共享两个方面：

| 记录字段 | 要说明什么 |
|---|---|
| `contract responsibility / independent source` | 测试负责什么保证，依据为什么独立于待审判定 |
| `focal boundary / test layer` | 真实生产入口、外部边界和单元、集成或契约测试层级 |

每组语义特征还须分别记录：

| 记录字段 | 要说明什么 |
|---|---|
| `partition / boundary role` | 输入按实际生产条件和契约属于哪一类（等价类），是否承担真实边界的检查 |
| `actual path` | 输入怎样经过生产决策和副作用，形成被观察的实际结果 |
| `oracle / verdict path` | 测试如何准备数据、取得预期、执行匹配并决定通过或失败 |
| `failure mode` | 哪类局部错误会被测试发现 |
| `requirement / risk dimension` | 涉及权限、租户、平台、并发或兼容等哪项独立要求 |
| `base / retained representative` | 原有覆盖，或当前准备保留的最小代表 |

**oracle** 是测试判断正确结果的依据，**verdict** 是最终通过或失败的判定。分别追踪实际结果和预期结果，可以发现两者共享错误来源、却仍然相等的情况。

组内每个成员只记录它与共同语义及代表测试的差异，没有差异写 `none`。测试名、变化说明、注释、断言中的值和测试数据只能帮助定位，不能自行创造行为要求或输入边界。

## 先区分真实输入类别，再选择代表

等价类（partition）是按实际生产条件和契约划出的输入类别，不是随意按测试样本分组。先找输入为什么会得到不同处理，再比较具体值：

| 输入 | 应先区分什么 | 通常不足以证明新增检测能力的差异 |
|---|---|---|
| 数值与长度 | 非法下界、恰好边界、内部值、溢出、饱和或精度边界 | 同一内部区间的普通正数，或同一超限类别中的普通长度 |
| 字符串与标识 | 空值、枚举、保留值、非保留值、格式和编码类别 | 同一非保留 key 下替换普通 value |
| 路径与前缀 | 根路径、匹配与不匹配、目录穿越、盘符、平台分隔符 | 相同深度和形状下换普通目录名或文件名 |
| 集合 | 空、单个、多个、重复、乱序、上限和分页边界 | 同一规模和顺序语义下替换普通成员 |
| 状态与身份 | 未认证、角色、租户、归属、前置状态、终态和重试 | 未参与权限、分支或输出的任意名称变化 |

相同生产路径不证明冗余，不同数据点也不证明独立价值。有限的权限、身份或协议集合中，不同成员可能有不同错误风险；集合外的普通值通常仍属于同一类别。没有分支的公式，也可以用能够区分漏项、错项、比较符、精度或溢出错误的输入，但不能臆造针对样本的特殊错误。

由生产校验、数据约束或协议确定的边界，有独立检查价值。下界、边界、内部值、上界及上界外，即使当前返回值相同，也不能自动互相替代。原来没覆盖的真实边界应直接保留，不要求再为每个相邻类别构造错误。只有名字自称“边界”，而生产条件和变化前契约没有分界时，仍按普通输入处理。

每组选择原有或最小保留代表，成员只与同一语义组的代表比较，不做全员两两比较。职责、输入类别、边界、生产或判定路径、错误方式、风险或测试层级不同，先分组；相关证据仍可同批读取。

## 根据变化选择要证明的分支

下表说明完整代码审查的必查分支。整体审计按当前受托判定的相应机制选择；窄审只取受托分支。形状触发调查，不直接决定问题成立；不确定变化是否影响判定时，先查清它的作用。

| 变化 | 必查分支 |
|---|---|
| 新增或修改用例、参数行、断言或快照 | 冗余信号；改变实际结果或预期路径时，同时检查失真和过约束 |
| fixture、mock 或 helper 改变真实调用、输入或预期来源 | 测试失真；固定额外判定属性时检查过约束；增加重复判定信号时检查冗余 |
| 预期与生产常量、schema、formatter 或转换共用来源 | 测试失真 |
| 断言固定顺序、完整对象、私有字段、精确诊断或调用形状 | 测试过约束 |
| 生产变化使既有测试的错误判定重新可达 | 测试失真 |

同一语义组共享分支选择结果，成员只分析自身差异。未触发的分支记录 `not applicable` 和理由；受托范围外则明确标为范围外，不混为已完成。

## 证明 T1：测试放过了应发现的错误

构造一个有独立契约依据、测试本来应拒绝的最小错误，分别追踪：

```text
错误输入或实现 → 生产路径 → 实际结果
错误输入或实现 → 测试准备和预期来源 → 匹配 → 最终判定
```

例如，预期和生产代码共用错误常量、辅助函数或转换，可能使两边同时出错却仍然相等。mock 绕过真实权限、事务、持久化或外部副作用，也可能使错误被放过。但必须证明当前受托判定让相关测试集合产生错误信心，并说明与本次变化或当前审计的关系；“还可以多测”不构成证明。

也要检查测试究竟负责哪一层。mock 或 stub 用预设结果替代下层实现，来检查调用方如何传播、映射或展示结果时，测试责任通常止于最近的未替换调用方，不自动包含下层生产者。

只有独立于待审测试的有效约定要求执行真实下层，或本次变化确实使测试集合失去了独立的真实路径检查时，才按绕过下层边界调查 T1。测试名字、预制错误文本或存在 mock，都不能扩大这项责任。

## 证明 T2 过约束：测试拒绝了合法变化

构造一种保持目标契约的现实变化，例如可扩展集合增加合法成员、无序结果改变遍历顺序、对象增加无关字段、内部 helper 等价重构，或逐项调用改为等价批处理。

沿生产结果与测试判定路径，证明测试会失败，并核对没有独立约定要求它固定的属性，才能作为 T2 过约束问题。报告时说明更窄、但仍完整验证行为的判定边界。

## 证明 T2 冗余：删除后不会损失检测能力

这一分支要回答：去掉一个测试后，会不会漏掉原本能发现的真实错误？先核对它是否承担独立责任，再比较重复部分，最后证明删除不会漏检。找到足以保留的理由就结束该成员的冗余调查；没有找到理由，仍不能直接断定它冗余。

这里只做静态删除分析，不授权修改或运行目标测试。冗余分支结束后，其他受托的有效性分支仍需完成；值得保留的测试也可能存在错误判定。

### 先检查必须保留的理由

沿以下差异查找独立检测能力：

- **行为或边界不同**：真实校验、原来未覆盖的明确边界、权限或归属、状态分支；
- **适用环境不同**：平台、运行环境、编码或外部使用方；
- **验证责任不同**：实际不同的单元、集成、契约测试层级，或独立的判定依据。

静态证明其中任一项提供独立价值，就保留该成员，无须继续证明它是否冗余。

例如，接口规定数量最多为 100，生产校验使用 `count <= 100`。已有测试只检查 50，新增测试检查 100。即使两者当前都成功，100 仍是原来未覆盖的真实边界：误将 `<=` 写成 `<` 时，50 发现不了，100 却能发现。已确认这样的新边界就足以保留，不必额外为相邻输入寻找错误。

### 再定位重复的判定信号

没有上述独立价值时，再检查以下重复形态。它们用于提出具体的冗余疑点，还不是删除结论：

- **重复断言**：同一测试观察相同状态、表达式并作相同判定，期间没有修改、await、重试、迭代、时钟推进或有副作用的求值。
- **相同或仅改名的测试**：忽略名称、class 与顶层包装、无语义差异的中间变量后，准备、实际调用、结果、预期和输入作用相同。
- **判定包含关系**：完整对象比较已经包含状态字段，完整集合判定包含相同成员，或原测试已覆盖新增的准备、实际结果和预期。
- **普通数据替换**：只改普通值、名称或局部变量，测试结构、输入类别、生产路径和判定方式相同。
- **重复准备**：准备相同还不够，调用、判定和可发现的错误也相同或已被包含时，才成为冗余疑点。

### 用删除分析检查是否会漏检

对具有共同冗余原因的一组成员做一次分析，不逐成员重复同一份证明。假设移除这些成员，寻找一种真实、局部、违反契约的错误：其余测试仍会通过，被移除的成员却会失败。这样的实例能够证明删除会损失检测能力，需要连起以下依据：

1. 什么错误或行为边界违反了要求；
2. 它怎样经过生产路径影响实际结果；
3. 为什么原有及保留的相关测试仍会通过；
4. 为什么当前成员会失败；
5. 错误来自生产表达式、校验、状态机、外部约定或真实风险，而不是为样本量身构造。

有效实例可能来自边界、权限、异常或终态、平台、编码、精度、并发、清理、外部使用方，以及现有生产代码能推导的漏字段、漏项、错误映射或比较符。不同名字、普通值、局部变量、fixture 描述、重复同一路径和“多一个样本更保险”都不够。

不能只假设实现会硬编码原测试值或预期结果来保留所有样本。只有生产代码、当前生产或契约变化，或独立有效约定，确实存在按该值、数据表、枚举成员或来源分支的证据时，才按此区别判断。待审测试、断言、预期和同期新增说明不能自行提供这个例外。

删除分析必须明确保留哪些测试。原来已有代表时，将新增成员与它比较；没有旧代表或进行整体审计时，先确定能够覆盖相应语义的最小保留集合，再检查其余成员。不能让两个重复成员互相充当保留依据，最后把两者都删除。参数化只减少测试代码重复，不增加错误检测能力。

### 同时满足以下条件，才报告冗余

1. **有明确的覆盖关系**：该成员的判定已被保留测试包含；或者它与代表的职责、输入类别、边界、生产与判定路径、错误方式及层级相同。
2. **没有独立价值被丢弃**：已核对前述行为边界、环境、测试层级和判定依据等差异，没有成立的保留理由。
3. **删除不会漏检**：已完成对照分析，明确保留集合，没有发现原来能检出、删除后会漏掉的真实错误。
4. **重复有实际成本**：能说明多出的失败信号或维护点。

第 3 项不能单独成立为结论。**没有想出一个错误，不构成冗余证明**；缺少第 1 项的包含或语义相同证据时，仍不足以报告。

## 核对变化关系，并按根因归并

每个疑点都记录最有力的合理解释：差异是否实际改变了校验、路径、结果、判定、独立要求或测试层级。“值不同”“actor 不同”“测试名不同”本身不足以证明独立价值。

增量审查核对旧版是否已有相同误判或冗余，当前怎样引入、扩大或重新触发；整体审计说明当前已有判定与保留集合。都要检查生产 finding 是否已覆盖同一根因。生产问题成立、测试只是同步背书时只报生产问题；测试有独立错误原因时保留 T finding。

冗余问题按共同业务行为、输入类别或边界、判定方式、可发现的错误和测试层级归并，记录为 **cluster key**，即同根因分组的标识。不要按批次、生成方式或“重复原有覆盖”合并不同生产符号、业务职责或外部边界。

同一根因中的完全复制、改名、普通数据替换、包含关系和重复断言，只作一条 finding 的不同证据。整个测试已冗余、内部又有重复断言时，优先报告整个测试的冗余；若测试本身有独立检测能力，则只报告其中真正重复的断言。

最终 T1 表示错误被放过；T2 过约束表示合法变化被拒绝；T2 冗余信号表示严格删除证明成立。后两者分别是缺陷和改进机会，不能只写一个“T2”而不说明。

## 保存进度并完成本批

沿用现有工作稿，不因为进入测试专项就新建账本。保留以下可恢复信息，英文键名用于与现有记录对应：

```text
batch ID / status：批次编号和覆盖状态
evidence：读取的修改前后代码及独立约定
coverage：census ID → fingerprint 的全部关联

family ID：
shared responsibility / focal boundary / test layer：共同职责、边界、层级

fingerprint ID：
partition / boundary role / actual path / oracle path / failure mode / risk dimension：
base / retained representative：
member deltas：每个成员与代表的差异
branch router：T1 / change-detector / zero-marginal / not applicable
candidate proof：violating / allowed / deletion / none
最强 veto：能够支持保留或排除疑点的证据
结论：保留 / T1 / T2-change-detector / T2-zero-marginal / 并入生产 finding

cluster index：cluster key → 全部 member ID → 唯一 finding 草稿 / none
```

记录中的 violating、allowed、deletion 分别对应错误接受、合法变化和删除分析；veto 是足以推翻当前疑点的证据，不是额外投票。它们是已有证明的记录方式，不要求再做另一套调查。

全部受托盘点关联和所选分支都应有结论或具体限制，范围外部分不计已审。冗余分支保留最小代表并解释额外成员的价值；其他分支不强加删除证明。同一 cluster key 跨批次只对应一条 finding。

测试通过不能替代这些证明，证据不足不能标为 complete。工作稿、部分覆盖输出和结束条件遵循[共同状态规则](../../review-state.md)。
