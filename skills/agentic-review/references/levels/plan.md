# 开发计划审查：从目标走到完整交付

计划审查关注两件事：按列出的工作全部完成后，目标是否真的实现；执行过程中允许出现的中间状态是否合理。计划不必重复架构全文，也不必把每个内部函数都列成任务。

共同调查、结论和复核规则从 Skill 入口读取，本文件说明开发计划特有的检查方法。

## 选择本次要检查的内容

普通审查承担表中标为“默认”的检查，按每行的适用条件调查；“明确委托”和“条件触发”的方法各按所列要求选择。明确窄审时，只使用所选方法及必要依据。

| 检查内容 | 方法 | 何时使用 |
|---|---|---|
| 所有任务完成后能否交付目标 | [意图对齐](../focuses/alignment.md)及下文交付检查 | 默认 |
| 依赖顺序和并行安排是否可行 | 下文依赖检查 | 默认 |
| 分阶段交付的中间状态是否安全 | 下文过渡检查；明确失败或中断审计时加[可靠性](../focuses/reliability.md) | 默认；有实际交付边界时检查 |
| 谁负责集成和有效验收 | [验证](../focuses/verification.md)的验收有效性方法及下文责任检查 | 默认 |
| 探索是否在相关投入之前完成 | 下文探索顺序检查 | 默认 |
| 是否存在可避免的协调成本 | [可维护性](../focuses/maintainability.md) | 明确委托：简化或成本审计 |
| 验证证据是否足以支撑保证 | [验证](../focuses/verification.md) | 条件触发：明确委托验证充分性审计，或当前阶段应完成相关验证 |

`simplify` 检查协调成本，不追求任务数量少。`harden` 检查实际交付阶段的中断、恢复、验收责任及验证充分性。计划不是实现，不要求每步运行一遍全套测试，也不要求现在执行所有未来实验。

## 先查清真正要交付什么

先读原始目标、有效架构决定、阶段范围和本轮授权，再读任务清单。计划不能自行删减目标，但明确批准的分阶段交付和非目标必须尊重。

登记需要交付的能力、依赖、必要集成、验证任务和过渡条件。不只登记作者已经列出的任务，否则被遗漏的工作永远进不了审查范围。无需规定统一的 `tasks.md`、任务数量、文件数或上下文比例。

## 检查全部任务完成后，目标是否成立

从用户最终能观察到的结果，倒推需要哪些能力、连接和工作：

```text
用户得到结果 ← 实际使用了能力 ← 必要连接已接通 ← 相关工作已完成
```

尝试构造一个“所有任务都按描述完成，但目标仍未实现”的实例。比如 API 和网页按钮分别建好，计划却把两者接通的工作排除在所有任务之外。明确遗漏且没有其他承担者时，可以构成缺陷。

反过来，如果任务描述或共同验收已经包含连接工作，就不能仅因没有逐字引用需求 ID 而报遗漏。结果和验收清楚时，也不要求补齐内部 helper 的流水账。

## 检查真实依赖和并行顺序

从工作需要的实际前置条件判断，不只相信 `depends_on` 等字段。检查是否先使用了尚未提供的接口约定、出现循环等待、两方各自决定了共享格式，或多个执行者竞争同一状态。问题应有一条计划允许出现的具体顺序和后果。

如果已有全局固定的约定、共同验收或明确集成人员解决了顺序，不因依赖图少一根箭头就要求重写。文件重叠不证明任务冲突，文件不重叠也不证明可以并行。

## 检查分阶段交付的中间状态

在实际交付阶段的结束、部分失败、暂停和回退处，检查旧路径是否保留、默认开关如何设置、新旧双方能否交互、数据能否按约定恢复。最终架构正确，不代表迁移顺序也安全。

只检查真实的交付边界。本地一次原子修改不要求每行代码都能独立部署；没有不停机要求时不发明零停机目标，但已有可用性和数据保证仍须保持。

## 检查集成和验收由谁负责

核对哪项任务产生验证证据、谁观察最终集成结果，以及证据何时产生。按[验证方法](../focuses/verification.md)，尝试找出局部验收全部通过、整体却失败的情况。

例如，所有任务只验收自己的产物，无人检查必要连接，可能使系统最终不能使用。验收行为清楚且责任已分配时，没有写死测试命令本身不是缺陷。

普通计划审查仍可报告具体错误验收，或明确遗漏的必要验证任务，无须用户特地说 `harden`。进一步审计验证充分性时，再按上表的条件选择对应方法，不泛化成“测试越多越好”。

## 检查探索和投入的先后关系

探索任务（常称 spike）用于回答会改变方案的问题。检查它要回答什么、结果如何观察、不同结果会怎样改变后续动作，以及哪些依赖任务在答案产生前不能开始。

先调查、再决定、再实施是合理计划，不因尚无调查结果就判不可执行。相反，如果计划让不可逆迁移或大范围实现依赖未经确认的接口能力，却把调查排在最后，应指出真实依赖问题。

预算和排期依据用户约束。不能仅凭模型估计“任务太大”就要求拆分，应说明已知资源冲突、不能并行的前置条件或当前交付要求。

## 把问题交给能够解决它的人

局部依赖或任务遗漏，可以由计划编写者修正。若可行路径需要改变已批准的能力、共享责任、接口或保证，应返回相应架构或需求决定。不能以“先做 v1”为由悄悄删除必须交付的目标。

架构本身相互矛盾时，保留原始依据和最小矛盾，不要求计划编写者靠增加任务实现不可能的要求。

## 交付和复核

受托目标的交付路径、相关依赖、中间状态及验收责任都应有调查结论或具体限制。疑点经过反证检查，成立的问题说明处理者和完成条件，按[共同结论要求](../findings.md)交付。

完成调查不等于计划没有问题。发现缺少接线或顺序错误，也可以完成本轮 Review；这里是静态审查，不证明实际执行一定成功，也不编造进度百分比。
