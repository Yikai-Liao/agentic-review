# 结论的证据要求

Review 的输出不只是“有错”或“没错”。有时已经能证明缺陷，有时需要用户作出决定，也可能存在有依据的改进机会，或当前还缺少必要的验证证据。本文件说明怎样区分这些结论，以及何时足以正式报告。

正式报告的问题条目称为 **finding**。问题的性质、处理优先级和处理状态分别回答“是什么问题”“有多急”“处理到哪一步”，不能互相代替。所选审查视角提供调查方法，并不直接决定这三个答案。

## 报告一条问题前，证据应满足什么要求

每条 finding 都必须能回答以下问题：

- **属于这次审查吗？** 增量审查应说明本次如何引入、扩大或重新触发问题；整体审计注明它是当前已有的问题；新提案指出本次准备确定的哪项内容存在问题。
- **凭什么判断？** 目标、约束或要优化的价值必须有来源，不能只来自待审产物自己的宣称。明确决定还要核对其适用范围与前提。
- **具体哪里不成立？** 给出可检查的场景和机制，说明谁的使用、任务或决定受到什么实际影响。缺少某个词、代码长得可疑、多数人赞同或“可能更好”都不够。
- **有没有能够解释它的合理情况？** 已核对最有力的保护、允许的实现选择、已有决定和合理取舍，它们仍不能排除问题。
- **怎样确认处理完成？** 定位能够实际修改的根因，说明应恢复的要求或应补齐的决定，并给出验收终点，而不是强制作者采用唯一实现。

任何一项不满足，都应保存排除理由或证据限制，不能给低严重度占位，也不能换一个类别发布相同猜测。

## 区分四种结论

### 缺陷：defect

已经证明产物违反了有依据的要求。证据应连起：应满足的要求、实际允许出现的触发条件或顺序、当前规定或机制，以及由此产生的错误结果和受影响者。

文档中的明确矛盾、静态代码推演也能证明缺陷，但应如实说明没有实测。尚未定义某个细节与已经证明错误不同；合法留待后续阶段决定的内容不算缺陷。

### 当前需要作出的决定：decision

有一项选择、授权或必要事实，当前的后续工作已经依赖它，却还没有得到解决。必须同时说明：

1. 哪项已计划的决定或交付依赖这个答案；
2. 不同答案会怎样改变责任、兼容性、保证、成本或执行路径；
3. 为什么不能通过读取现有资料解决，也没有合法安排在依赖它之前由其他人解决；
4. 最小需要回答的问题、谁有权回答，以及受影响的范围。

缺事实时提出具体调查请求；缺取舍时说明真实选择和代价。没写重试次数、没测某项指标本身不构成此类问题；也不能因缺陷证明失败，就改报“建议人工确认”。

### 有依据的改进机会：improvement

没有证明违反要求，但能证明存在值得考虑的更好做法，而且本次范围确实包括这类优化：用户明确委托，或所选层级默认承担。

证据应说明真实任务与评价目标、当前机制带来的成本、保持必要保证的可行替代，以及收益与迁移、新耦合、学习等代价的比较。某些方法还要求更严格的证明，例如删除测试前确认不会损失独立检测能力。

改进机会默认不阻断交付。若已明确违反约定的目标，应按缺陷证明；“用户希望简单一点”不能变成审查者要求一切符合个人风格的授权。

### 当前验证不足：verification-gap

当前已经需要用验证结果支撑某项保证，但现有验证无法有效识别相关错误。必须同时具备：

1. 有独立依据的、当前阶段应完成的验证要求；
2. 一种来自真实机制或边界的局部错误；
3. 对照分析表明该错误违反保证，却不能被现有相关验证发现；
4. 最少增加什么观察，就能区分正确与错误，同时保留相邻的合法行为。

这种结论不表示生产实现已经出错。低覆盖率、以后可以多测或未知本身都不成立。没有受托调查验证充分性，也不存在当前必须完成的独立验证要求时，不能因普通审查顺带发现“缺测试”就增加 finding。

已有验收判定会接受错误或拒绝合法行为，可以是缺陷；验证缺口则指尚需补充有效区分证据。两者具体证明见所选方法，同一根因不重复报告。

四种性质适用于不同视角，不为每个新视角另造一套类型。确实无法表达新的成立方式时，由维护者先说明需要什么证据、哪些情况能推翻它，再统一修改本文件；执行中的审查者不临时增加宽松类别。

## 判断优先级，并找到正确的处理者

先确认成立，再根据实际影响、当前交付和紧迫性判断：是否阻断相关交付或决定，是否需要修正但可隔离推进，还是可独立安排。不是所有问题都阻断，也不是所有阻断都影响整个项目。代码层等可以定义展示标签，但标签不能代替证明。

为每个可独立处理的根因分配一个稳定的本轮编号，例如 F1。修改同一处就能消除多个现象时，合为一条并保留相关验收；只有需要独立修复的原因才分开。优先报告生产违约，而不是重复报告为它背书的测试；明确矛盾也不再派生一条“需要决定”。原有问题没有变化时，关联原编号，不制造新发现。

根据修改所需的权限分配处理：

- 在既有要求和授权内就能解决，交给本层的编写者。
- 必须改变共享责任、接口、范围、重要保证或已接受代价，保留反例，交还给有权决定的人或相应上层。
- 上层文件本身与原始目标冲突，并列双方依据，不因它“已批准”就要求下层实现错误。

处理者不明确时，说明待确定的责任及证据，不自行授予权限。接受业务代价不授予运行、发布或部署权限。

## 输出

先给出一句当前结论，把关键范围限制紧邻结论说明；随后列出需要处理的问题。每条都应能独立读懂：

```text
F1 [性质；相关视角；优先级；处理者]：什么条件下会造成什么后果
问题与依据：预期、实际、所审版本和位置、最短因果解释，以及已排除的合理解释。
处理完成条件：恢复什么要求或补齐什么决定，如何复核原触发及相邻合法行为。
证据边界：哪些是静态推演，哪些已有实测，哪些尚未验证。
```

位置指向所审版本中最小可操作根因。代码可用行范围，需求和设计可用条款或明确遗漏的责任位置，不虚构 diff 行。简单问题用短段即可，模板不要求每条填满一张表。

问题的处理状态保存在工作稿的 F 编号条目中，按[状态变更的证据要求](review-state.md#状态变更需要什么证据)更新；不是每条新 finding 都要另加公开状态字段。代码层的 P 标签按已证明的影响表达严重度，可用于说明处理优先级；T 标签说明测试失败方式。二者都不能代替问题性质或处理状态。

没有 finding 时，说明所审变化或要求为什么在已查范围内与依据一致，并保留证据限制；不填满空章节，不宣称全面正确或批准合并。完整调查和排除理由留在工作稿，完成与复核按[工作稿规则](review-state.md)处理。

直接相关的历史问题或决定，即使没有产生新 finding，也要关联原记录并说明当前状态。未解决的仍写未解决，部分修复说明剩余触发，已接受的说明具体范围，不把接受写成修复。仅触及原问题时说明本次影响，不重复创建条目。不为此扫描无关历史，也不编造链接，使用已有稳定 ID 或可恢复来源。

任务要求的输出格式只改变封装，不改变判断。提交前需要刷新讨论或状态时，先完成再生成结果。审查规则缺失、会话压缩后或无法确认输出格式时，从任务指定的可信来源恢复，不能根据待审产物或历史结果猜测本轮接口。

如果固定输出格式无法表达一个已成立的结论，保留工作稿并明确报告接口限制；没有授权不能另发评论，不能假冒允许的标签，也不能静默丢弃。提交成功后结束本轮，不继续重复调查或发布。
