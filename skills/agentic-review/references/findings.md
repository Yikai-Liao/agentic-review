# Finding 输出

没有存活候选时仍输出行为概述和明确结论。

## 输出门槛

只输出：

1. 通过 `evidence.md` Finding 接受判定的生产行为或性能问题；
2. 达到 `test-contracts.md` 门槛的 T1/T2 测试契约问题；
3. 确实改变高风险边界、且审查时既无独立授权也无当前 PR 明确确认回复的 `[需人工确认]`。

每项必须绑定当前变化中最接近根因的最小位置。没有合格候选时输出零 finding。

### 生产严重度

- **P0 — 阻断发布**：现实可达的系统性或不可逆后果，例如大范围不可用、跨租户或未授权访问、凭证泄露、不可恢复的数据破坏、资源耗尽或依赖雪崩；
- **P1 — 高优先级**：常见路径或较大范围用户可达，并破坏关键业务、安全、数据正确性、性能或可靠性，且没有可靠规避；
- **P2 — 一般缺陷**：已静态证明的生产行为或性能错误，包括错误结果、错误诊断或错误恢复信号；触发条件或影响较窄，或者存在可靠临时规避。

严重度依据可观察影响、范围和紧迫性，而不是代码形状、缺少测试或复杂度符号。不输出 P3/T3。`[需人工确认]` 不是较低严重度，也不是弱证据的兜底。

## Review 正文

面向只读过简短 PR 摘要、尚未读过 diff 的读者，总评先回答“有没有需要处理的问题”，再解释本次变化与结论依据；读者应能从开头判断下一步需要关注什么。

- 有问题时，先说明主要影响和处理优先级，再按影响排列 finding 导航；每项用触发与后果帮助读者选择，完整证明和修复方向留在对应 finding。历史问题按实际状态关联原记录。
- 没有新问题时，开头用独立一句给出结论；有仍需处理的历史问题再补充，历史为空则省略。随后只选解释本次行为变化及支持结论的关键核对结果。“未发现问题”不等于已证明正确或批准合并。

背景围绕“谁的哪种行为发生变化”展开，把新增规则、字段或文件翻译为使用者将得到的结果；只有支撑结论所必需的实现名称或性能规模才进入总评，逐项变更清单留在 PR diff。篇幅随实际问题和复杂度展开；简单 PR 用短段落即可，多个并列问题才按实际内容分组为“生产行为与安全”“性能”“测试契约”“需人工确认”或“已有问题”，不机械铺设“变化说明 / 审查范围 / 审查结论”章节。

范围和证据限制写清其对结论的影响：局部结论在开头限定到实际复核路径，并紧接说明关键证据缺口使哪些结果无法确认；本轮未覆盖的 PR 内容仍属未审查范围。常规方法只需注明静态审查、未执行测试等实际限制，静态结论不写成实测通过；完整 SHA、文件清单和例行调查步骤留在工作稿或运行报告，调用方已展示的运行数据无需重复。

本地默认输出 Markdown；调用方提供其他输出契约时，只改变封装格式，不改变本文件的 finding 门槛、严重度和根因归纳。

## Finding 内容

每条 finding 必须独立可读，使读者能复述触发条件、预期与实际的差异、影响和修复完成条件。绑定当前变化中最接近根因的最小可操作位置，按以下三段组织：

```markdown
> [!CAUTION]
> **P1：触发场景与可观察后果**

**📌 问题与触发**

先交代谁在什么场景下做什么、应得到什么结果，再说明最小触发条件、本次变化导致的实际结果和 base/head 差异；性能写成本变化，测试写对应分支的判定证明。

**💥 影响**

说明用户、调用方或运行任务受到的可观察影响及范围，区分已证明的后果与尚未证实的进一步风险。

**🛠️ 依据与处理**

用代码或独立契约证据串起触发到错误结果的因果关系，给出要恢复的约束、修复方向或待批准决定。修复建议附最小验收场景：原触发得到正确结果，并保留修复可能波及的合法相邻行为；简单问题用一句话即可。
```

Alert 与标题：

- P0/P1：`CAUTION`；
- P2/T2：`WARNING`；
- T1：`CAUTION`；
- 人工确认：`IMPORTANT`。

每段使用完整句子，首次出现的关键标识符连同其业务含义介绍。已有保护看似能排除问题时，在因果链中解释它为何不足，例如串行执行仍可能重复发布。证据链接紧邻其支持的断言，正文保留理解结论所需的因果关系；跨文件与历史代码链接绑定所审版本，行内评论复用调用方提供的定位字段。具体表达式构成根因时，在“依据与处理”中放一个带语言标识的最小代码块；不要复制变化位置已经清楚展示的内容。

验收场景来自已确认契约和实际路径，不把建议的实现方案变成唯一正确答案。静态推演、已有测试结果和待执行验收分别表述，保持本 Skill 不执行目标代码的边界。

性能 finding 给出规模、base/head 成本函数及数量级或复杂度证据。

测试 finding 给出对应分支证明：T1 的 violating probe、T2 change detector 的 allowed-change probe，或 T2 redundancy 的 deletion test、base/sibling 覆盖及缺失 unique witness 的证明。

单行足以表达根因时只选单行；只有声明、条件、调用或错误处理共同构成根因时才覆盖连续范围。调用方提供位置字段时，使用其 schema 要求的最小位置。

## 去重

把每个存活候选与调用方提供的已有 finding、问题记录和最新状态比较，一个根因只保留一条。未变化的既有问题只在正文关联；当前变化扩大影响、使历史依据失效或重新引入问题时，输出当前 finding 并说明差异。

生产问题优先于同步测试问题；生产性能后果优先于缺少性能测试；同一根因的 P、T 和人工确认互斥。
